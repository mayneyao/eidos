## Design Context

### Users

Eidos is for people who manage personal knowledge and structured data locally. In a file-based Space, they work in a desktop app for long sessions and need to browse, create, search, rename, move, and edit files without losing the direct relationship to the folder on disk. In Eidos File Web, they want to open, inspect, test, and edit local `.eidos` files quickly while staying confident that the data remains under their control.

### Brand Personality

Focused, capable, and calm. The interface should feel like a dependable professional tool: information-dense without feeling crowded, direct without feeling crude, and quiet enough that the user's content stays in focus.

### Aesthetic Direction

For the file-based Space shell, use VS Code's Explorer as the interaction and density reference: compact rows, strong alignment, progressive disclosure of secondary actions, and desktop-native window chrome. Preserve Eidos's neutral theme tokens and support both light and dark themes. Avoid dashboard cards, oversized controls, decorative gradients, generic AI-product styling, and unnecessary visual effects.

For Eidos File Web, use a compact, flat workbench with the data canvas as the visual center. File identity, state, and common actions should share one quiet hierarchy built from neutral surfaces, hairline separators, and precise typography.

### Design Principles

1. Use **Space** consistently as the product concept; never introduce a competing container term.
2. Keep files visibly primary: the folder is the source of truth, and navigation should feel immediate and predictable.
3. Optimize for scanning with compact rows, consistent indentation, restrained icons, and clear selected, hover, focus, loading, and drop states.
4. Reveal secondary actions on hover, focus, or contextual menus while keeping creation and navigation easy to discover.
5. Respect desktop chrome, keyboard workflows, reduced motion, theme contrast, and resizable layouts.
6. Keep Space switching on the Space name at the top of the desktop Explorer.
7. Treat modal dialogs as an exceptional interaction. Prefer inline editing, header menus, anchored popovers, and progressive disclosure for routine creation and configuration; reserve modals for destructive confirmation or decisions that must block the current workflow.
8. Give every Settings section exactly one surface owner. Codex-style setting rows may share one bordered group, but rich modules that already render cards, lists, or callouts must keep those native surfaces without another generic card around them.
9. Reorder Tables, Views, and Fields through one consistent drag-and-drop pattern with a keyboard-operable drag handle. Never add separate “Move up” or “Move down” buttons or menu items for structural ordering; ascending/descending data sort remains a distinct semantic control.
10. Give every field-type choice the same canonical icon in both its trigger and menu row. Render configured Select and Multi-select values with their catalog color everywhere they appear; never fall back to text-only presentation while color metadata is available.
11. Keep the Eidos File workbar query/layout cluster in the order Search, Filter, Sort, Fields. Treat Fields as the primary field browser: visibility, drag ordering, and property inspection use separate hit targets. Card layout consumes the visible-field set and owns only card content/appearance, never a second competing visibility model.
12. In Eidos File Web, give the data canvas maximum space. Combine file identity, live state, search, and preview actions into one compact workbar; keep temporary-copy and Worker details available as secondary accessible context instead of a persistent footer.
13. Follow the Eidos Lite theme specification: components consume semantic tokens, only the Space Explorer owns a persistent tinted surface, and chrome plus editor themes switch from one resolved appearance without remounting content.
14. Keep local interactions visually continuous. Loading must never replace existing UI or occupy an incoming content surface before its content arrives. Preserve the current UI and show only a subtle status beside it until the next content is ready. Treat content → loading → content as a forbidden anti-pattern. Follow the rules below for navigation and asynchronous updates.
15. Expose Sync and Settings options only when they support a useful user decision. Use safe defaults for encryption and secure password storage; keep credential lifecycle, device registration, and normal access grants out of the daily workflow. Consolidate duplicate entry points and describe actions by their actual scope. Preserve explicit device authorization, genuine file blockers, and actionable password, conflict, and quota recovery.
16. Treat native window controls as reserved layout space. On Windows and Linux, the rightmost top-level surface owns the caption-button inset, including file preview, history, and Sync sidebars; transfer that inset when a sidebar opens or closes. Derive the inset and title-row height from Window Controls Overlay geometry (`titlebar-area-*`), and size adjacent action hit targets and glyphs from those same metrics rather than independent `rem` sizes. Keep actions non-shrinking and outside drag regions. Verify long titles, narrow windows, sidebar transitions, maximized/restored windows, application zoom (80%, 100%, 125%, 150%), and Windows display scaling (100%, 125%, 150%); macOS traffic lights retain their own platform layout.
17. Adapt sidebar header actions to the operating system across file preview, history, and Sync, including account and Close controls. On Windows and Linux, place actions immediately after the title, then leave drag space and the reserved native caption-button inset on the right. On macOS, traffic lights are on the left: keep the title on the left and align the action group to the upper-right edge of the sidebar. Do not apply the Windows/Linux workaround to macOS. On every platform, let long titles shrink and truncate while actions remain visible, non-shrinking, and outside drag regions. Product demos must match the platform chrome they depict.

### Android Native Search

- Keep Compose and the system font, including system font scaling. Use Material typography roles rather than fixed text sizes: `titleMedium` for search headings, `bodyLarge` for input and result titles, `bodyMedium` for paths, and `bodySmall` for status.
- Use a 16dp content inset and an 8dp spacing grid. Keep icon actions at least 48dp; compactness must not reduce touch targets.
- Space search and plugin search share `EidosSearchField`, including shape, border, clear action, and keyboard Search behavior. The caller owns outer spacing.
- Use the neutral semantic palette in `EidosTheme.kt` for light and dark appearances. Search sheets and their result rows share `surface`, with a quiet divider below the search controls. Do not put separate colored cards behind results.
- File and record results use the same two-line hierarchy, icon alignment, and trailing action width. Truncate long text visually while retaining its full accessible label. Keep existing file actions available.
- Keep search controls and results mounted while searching; preserve the query when returning from a result. Search owns input focus on opening; the keyboard Search action dismisses the keyboard without restarting the live query.

### Loading, Navigation, and Focus Continuity

Eidos Lite is a local application. Most reads finish quickly enough that a loading screen is more disruptive than the wait itself.

- **Forbidden anti-pattern: content → loading → content.** Never replace an application, main editor, sidebar, record, table, view, list, or history surface with a loading screen, spinner, skeleton, or blank placeholder while fetching its next content. Do not mount a loading placeholder in the incoming main area and then replace it with the destination content. This intermediate replacement causes visible flicker during rapid switching, even when each request is fast. A delayed spinner, loading-only `Suspense` fallback, fade, or minimum display duration does not make this pattern acceptable. Reject branches such as `loading ? <Loading /> : <Editor />` when they replace the content surface.
- **Reuse ready content.** Use cached data immediately for record, file, table, view, and history selection. Keep compatible editor sessions mounted while loading a replacement; do not clear the current model or change component keys just because a request starts. Preserve scroll and editor state where appropriate.
- **Keep identity accurate.** Swap content and its identity together. Do not label previous content as the newly selected record or commit. While retaining previous content, prevent edits or destructive actions from targeting the pending selection by mistake. Discard superseded async results so a late response cannot replace the latest selection.
- **Keep progress beside existing UI.** Loading feedback must be a subtle addition next to an existing control, title, toolbar, or surface border. It must not cover, hide, dim, resize, or replace the content, move focus, or shift the layout. For a first load without previous content, keep the existing application shell and stable destination geometry; attach progress to existing chrome instead of putting a loading placeholder in the destination area.
- **Show progress only when useful.** For a noticeable wait, use the small, localized indicator described above. Around 200 ms is a reasonable starting point for delaying that indicator, not a mandatory constant; cancel it on completion, supersession, or unmount. This delay applies only to the adjacent status, never to content replacement. Do not impose a minimum loading duration or delay ready data or errors for animation.
- **Fix the data flow first.** Trace event → state → route → read → render before adding visual delays. Recording a route for an already loaded selection must not clear and reload the same data. Back/forward and refresh still restore from the route. Give each read one owner, and select the target table before mounting its editor. Timers, opacity transitions, and hidden loading text must not conceal redundant reads or unnecessary remounts.
- **Keep keyboard focus intentional.** An explicit editor-mode switch focuses the destination editor when ready and preserves the draft. Use supported focus APIs and consistent initial caret placement; Markdown starts at the document beginning when no existing selection is being restored. Modal search and dialogs own focus while open; background editor updates must not reclaim it. Prefer focus-isolating modal primitives over repeatedly forcing focus back.
- **Verify fast and slow paths.** Check cached/fast reads, delayed responses, failures, and rapid A → B → C selection, plus back/forward and refresh. Reject any intermediate loading surface or flash of cleared content; the existing UI must remain until ready content and its identity can be swapped together. Verify no duplicate reads, stale-response rejection, preserved drafts, and focus ownership. Browser or Electron verification is needed to assess visual flicker and native focus; DOM-only tests do not prove them. Genuine slow operations, errors, and missing resources still need clear feedback and recovery actions.
