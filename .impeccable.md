## Design Context

### Users

Eidos is for people who manage personal knowledge and structured data locally. In a file-based Space, they work in a desktop app for long sessions and need to browse, create, search, rename, move, and edit files without losing the direct relationship to the folder on disk. In Eidos File Web, they want to open, inspect, test, and edit local `.eidos` files quickly while staying confident that the data remains under their control.

### Brand Personality

Focused, capable, and calm. The interface should feel like a dependable professional tool: information-dense without feeling crowded, direct without feeling crude, and quiet enough that the user's content stays in focus.

### Aesthetic Direction

For the file-based Space shell, use VS Code's Explorer as the interaction and density reference: compact rows, strong alignment, progressive disclosure of secondary actions, and desktop-native window chrome. Preserve Eidos's neutral theme tokens and support both light and dark themes. Avoid dashboard cards, oversized controls, decorative gradients, generic AI-product styling, and unnecessary visual effects.

For Eidos File Web, use a compact, flat workbench with the data canvas as the visual center. File identity, state, and common actions should share one quiet hierarchy built from neutral surfaces, hairline separators, and precise typography.

### Design Principles

1. Use **Space** consistently as the product concept; never introduce a competing container term.
2. Keep files visibly primary: the folder is the source of truth, and navigation should feel immediate and predictable.
3. Optimize for scanning with compact rows, consistent indentation, restrained icons, and clear selected, hover, focus, loading, and drop states.
4. Reveal secondary actions on hover, focus, or contextual menus while keeping creation and navigation easy to discover.
5. Respect desktop chrome, keyboard workflows, reduced motion, theme contrast, and resizable layouts.
6. Structure the desktop sidebar in three layers: primary work modes at the top, the active mode's content in the middle, and the current Space switcher at the bottom.
7. Treat modal dialogs as an exceptional interaction. Prefer inline editing, header menus, anchored popovers, and progressive disclosure for routine creation and configuration; reserve modals for destructive confirmation or decisions that must block the current workflow.
8. Give every Settings section exactly one surface owner. Codex-style setting rows may share one bordered group, but rich modules that already render cards, lists, or callouts must keep those native surfaces without another generic card around them.
9. Reorder Tables, Views, and Fields through one consistent drag-and-drop pattern with a keyboard-operable drag handle. Never add separate “Move up” or “Move down” buttons or menu items for structural ordering; ascending/descending data sort remains a distinct semantic control.
10. Give every field-type choice the same canonical icon in both its trigger and menu row. Render configured Select and Multi-select values with their catalog color everywhere they appear; never fall back to text-only presentation while color metadata is available.
11. Keep the Eidos File workbar query/layout cluster in the order Search, Filter, Sort, Fields. Treat Fields as the primary field browser: visibility, drag ordering, and property inspection use separate hit targets. Card layout consumes the visible-field set and owns only card content/appearance, never a second competing visibility model.
12. In Eidos File Web, give the data canvas maximum space. Combine file identity, live state, search, and preview actions into one compact workbar; keep temporary-copy and Worker details available as secondary accessible context instead of a persistent footer.
13. Follow the Eidos Lite theme specification: components consume semantic tokens, only the Space Explorer owns a persistent tinted surface, and chrome plus editor themes switch from one resolved appearance without remounting content.
