Browser recovery, local history, Sync, and backups protect different copies of
your work.

| Mechanism                    | Protects against                                             | Does not replace                                |
| ---------------------------- | ------------------------------------------------------------ | ----------------------------------------------- |
| Browser recovery copy        | Closing or reloading with unsaved Web edits                  | Saving the file or keeping backups              |
| System Trash                 | Files deleted through the Eidos Lite Explorer                | Version history or off-device backup            |
| Graft local history          | Returning to named states and reviewing supported changes    | A separate backup device or remote              |
| Eidos Sync (private preview) | Continuity between a local Space and an authenticated remote | Local ownership or explicit conflict handling   |
| Ordinary backup              | Device loss, corruption, or an unwanted history operation    | Runtime validation and a tested restore process |

## Web recovery

The Web Editor keeps recoverable work in browser-private storage where the
browser supports it. Recover the work, then save or download a durable file.
Clearing site data can remove browser recovery.

## Lite history and Sync

Eidos Lite uses Graft for local checkpoints and row-aware history. Local work
does not require an account. Sync is an invite-only private preview and has explicit sign-in,
authorization, fetch, analysis, pull, validation, and push states. A Sync
failure should leave local files usable and present a recovery action instead
of hiding the failure.

Joining the waitlist does not grant Sync access automatically. Until access is
approved, Lite remains fully local and does not provision or connect a remote.
Keep normal file backups regardless of Sync access.

An approved connected Space can incrementally Pull a clean fast-forward update,
cancel safely during close, reopen its resident Eidos File handles, and retry.
If Local and Hosted histories diverge, Lite stops before materialization and
preserves both sides through the explicit recovery-copy flow; it does not force
push or choose a merge winner.

## Read the Sync stages

Connecting or cloning a Space is a multi-stage operation: access is checked,
the local or remote plan is prepared, objects are transferred, the resulting
files are validated, and the connection state is finalized. Byte progress,
speed, and estimated time are meaningful only after the transfer size is known;
planning may therefore appear before a total.

During ordinary Sync:

- **Fetch** learns and downloads Hosted history and objects.
- **Analyze** compares stable local and Hosted commits.
- **Pull** applies a clean Hosted advance to the local Space.
- **Merge** appears only when both histories contain new work that cannot be a
  clean fast-forward.
- **Push** publishes the resulting local commits after validation.

One pack request may contain several commits and objects. The number of commits
does not imply one full download per commit.

## If Sync needs attention

1. Keep the local Space and recovery copy; do not delete either to clear a status.
2. Open Sync details and identify the failed stage and retryable action.
3. Commit or intentionally discard unrelated local working changes before Pull.
4. A merge with zero unresolved conflicts should complete without presenting a
   conflict-resolution screen. If a zero-conflict screen remains open, capture
   the state and retry instead of inventing a conflict choice.
5. After a successful Pull, let Lite reopen resident Eidos File sessions so
   editor caches are invalidated before continuing work.

If retry repeats, capture the Lite version, operating system, Space identifier,
stage, error record, and relevant JSONL log. Local files should remain usable
while Sync is stopped.
