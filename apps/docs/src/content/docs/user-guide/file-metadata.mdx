**File Metadata Management** shows files in a folder as table records.
Add fields such as Status, Rating, or Tags to organize files.

The configuration lives in `files.eidos`.
Custom values live in the physical file attributes.
These are separate storage locations.
Copying the configuration file alone does not copy your tags.

---

## 1. Quick start

Start in the folder you want to manage:

1. **Create a file**: In the Eidos Lite sidebar, select New File (`Cmd/Ctrl + N`). Choose **Eidos** as the file type.
2. **Enable management**: Turn on the **File Metadata Management** toggle. The filename becomes `files.eidos`. Select **Create**. Each folder receives one configuration file. Eidos never overwrites an existing file.
3. **Start tagging**: Open the table. Select the **+ (Add Column)** button in the header. Enter a property name such as "Status", "Rating", or "Tags". Record metadata directly on your files as you would in a spreadsheet.

---

## Folder browsing and metadata configuration

Right-click a folder and select **Show this folder** to make it the sidebar root.
The breadcrumb path above the tree returns to ancestor folders.
**Sort files** beside Search offers name, modification time, and file type in ascending or descending order.
Folders stay first.
Eidos remembers your sort preference across sessions.

A subfolder `files.eidos` inherits custom fields, types, options, settings, attribute namespace, and storage keys from the nearest parent configuration.
This copies configuration at creation time.
Later changes in a parent folder do not overwrite child configurations.
Inheritance does not copy files or property values.
Configurations sharing a namespace and storage key read the same attributes on a physical file.

Existing metadata files with other names remain directly usable.

## 2. Daily workflow and file safety

- **Original files stay in place**: Editing custom fields changes file attributes, not file content bytes.
- **Automatic disk change detection**: When you add, rename, or delete files in your operating system, the table updates in real time.
- **Open physical files**: The read-only `file` cell opens the file in your system viewer. Local files, including large videos, open without loading full file bytes into the editor. Image thumbnails retain preview size limits.

CSV import can create an ordinary table alongside `files` in the same `.eidos` file.
Ordinary tables support Relations to other ordinary tables.
The filesystem-backed `files` table cannot be a Relation source or target.
URL fields work normally.

## 3. Scope of management

**An `.eidos` file with File Metadata Management enabled scans its containing folder and all subfolders.**

It does not scan parent directories.
It does not follow symbolic links.
It ignores excluded files.
A table created in a subfolder scans only that subfolder and its descendants.

## 4. Nested folders and shared attribute mechanics

Complex projects often contain nested subfolders.
A parent folder and a subfolder can each create a `files.eidos`:

### Independent layouts and configurations

The `.eidos` file in the parent folder and the one in the subfolder are separate documents:
Layouts, view styles, filter criteria, and sort rules remain independent.
The parent table can include files in a subfolder whether that subfolder has its own `.eidos` file or not.

### Shared underlying metadata on physical files

Custom attributes record directly in physical file extended attributes:

- **Field names are attribute keys**: New fields use their exact names as storage keys. Tools and tables that use the same namespace and key share values.
- **Field names cannot change**: Metadata fields do not support renaming. Existing fields with generated `field_…` keys retain their mapping. Opening a file does not overwrite external attributes.

### Important precautions

1. **Edits update physical file attributes**: Tables that share a storage key observe each other's edits.
2. **Moving files**: Renaming a file on the same filesystem preserves attributes. Copying files across drives depends on the filesystem. The destination table needs the same namespace and storage key to read values.
3. **Deleting fields versus clearing cells**:
   - **Deleting a column** deletes the column and clears the attribute from files in the table. This affects other tables sharing that attribute.
   - **Clearing a cell** clears that single attribute from the physical file.
4. **Attribute portability**:
   - macOS and Linux use extended attributes. Windows uses alternate data streams. The filesystem must support them. Check your backup tool to make sure it preserves external attributes.
   - Moving files through tools that strip extended attributes can delete this metadata. Basic FAT32 drives do not support extended attributes.
5. **Transaction boundaries**: The rollback journal lives in memory while the process runs. It does not provide crash atomicity or protection from other programs editing the same files.

## 5. Built-in system fields

The system extracts physical file properties as read-only fields:

| Field | Type | Description |
| :--- | :--- | :--- |
| `name` | Text | Physical filename (e.g. `Photo.jpg`) |
| `path` | Text | Relative path from the folder root (primary label) |
| `extension` | Text / Select | Lowercase file extension (e.g. `jpg`, `mp4`, `pdf`) |
| `size` | Text / Integer | File size formatted in KB, MB, or GB |
| `mimetype` | Text | Media type (e.g. `image/jpeg`, `video/mp4`) |
| `file` | Attachment | Local file handle for thumbnails and previews |
