The template selector, target checks, checksum output, and registry helper below
are implemented in the current source checkout. They require the next
plugin-tools / CLI release; published plugin-tools 0.2.0 does not include them.
Before release, build plugin-tools in this repository and run its
`bin/eidos-plugin.mjs` directly. Source examples and APIs use SDK 0.2.0.

## Choose a starter

```sh
npx @eidos.space/plugin-tools templates
npx @eidos.space/plugin-tools create my-plugin --template table-action
# Equivalent project creation, with no Node.js needed for this step:
eidos plugin create my-plugin --template table-action
cd my-plugin
npm install
npm run check
```

| Template                | Capability and entry point           | Example                                   |
| ----------------------- | ------------------------------------ | ----------------------------------------- |
| document-view (default) | File View → Document View; Open with | CSV editing, save and undo/redo           |
| eidos-view              | File View → Eidos View; Open with    | Tables and fields in an .eidos file       |
| table-view              | Table View; table view menu          | Record count with change observation      |
| table-action            | Table Action; table context menu     | Mark a checkbox, pagination and progress  |
| page                    | Page View and workspace action       | Navigation page and command-palette entry |
| theme                   | Eidos Lite host theme                | Standalone light/dark palette and fonts   |

Ordinary plugin projects use `src/`; the theme starter needs only `plugin.json`.
Node and Rust use the same template catalog and source files. The code starters
use plain TypeScript, not React. Add React explicitly
using the [guide](/plugins/guide/#using-react-and-ui-components) when needed.
Unknown options and templates are errors.

## Check the intended host

```sh
npm run check -- --target lite
npm run check -- --target cli --json
eidos plugin check . --target cli
eidos plugin doctor dist/local.my-plugin-0.1.0.eidos-plugin
```

An ordinary check validates code and reports both host profiles. A target check
also fails if that profile cannot run the plugin. These profiles belong to the
installed tool version; they do not detect the installed Lite application.
`eidos plugin doctor` reports the actual CLI host's contract.

| Host profile     | Plugin API | Supported scope                                                                                            |
| ---------------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| Lite development | 1.6.0      | Document, Eidos, table and page views; actions, settings, Markdown permissions, and standalone host themes |
| CLI 1.4 Serve    | 1.0.0      | Table views and declared browser network/workers                                                           |

SDK npm version, plugin version, and host version are different from the plugin
API contract. Keep `apiVersion: 1`; declare a minimum contract when required:

```json
{ "requires": { "pluginApi": "1.1.0" } }
```

The tools derive required features from declarations. Authors do not maintain a
separate capability list. Packages with `requires` use envelope format 2; legacy
packages without it use format 1. Let the packer produce the envelope.

## Configure an .eidos file

Narrow `ctx.binding.kind === "eidos"` before using `ctx.binding.file`.
The bound file supports:

- `listTables()`: table IDs and names.
- `readTable(tableId)`: field metadata.
- `readPluginConfig(tableId)`: this plugin's table configuration and version.
- `writePluginConfig(tableId, { value, expectedVersion })`: version-checked configuration writes.
- `connections.configured(id)` and `connections.request({ connection, body })`.

Configuration belongs to the plugin's namespace in the table settings JSON.
It moves with the .eidos file. Keep credentials out of this configuration.
This context does not provide arbitrary SQL or general record mutation.

## Dynamic table actions

Register a `TableActionProvider` with
`ctx.actions.registerTableProvider(actionId, provider)` during activation.
The manifest action uses `context: "table"`, `access: "write"`, and the
`table/context` placement. The returned registration is disposable.

- `getItems({ table, signal })` returns items with `id`, `title`, optional SVG
  path icon, and `targets` (`row`, `selection`, `view`).
- `run(ctx, itemId)` executes the selected item. Read current schema and
  `table.pluginConfig.read()` instead of keeping a stale menu snapshot.
- `ctx.target.count` and `target.read({ offset, limit, fields })` traverse
  the frozen target scope, including all filtered records. Do not substitute
  only the rows currently loaded in the grid.
- `target.update({ readToken, values })` writes through the host with stale-read
  protection. Do not replace it with direct SQL.
- Check `ctx.signal` between reads and writes. Await writes and propagate failures.
- `ctx.task.report({ completed, message })` updates the host-owned task window.
  Lite provides run undo/redo. A completed count includes unchanged records.
- Before the first write, call `task.preview(rows)` once with 1–3 real read tokens
  and validated sample outputs to declare the output fields. Subsequent writes
  must stay within those fields; sample records must match the declared values.
  The call is required despite its legacy name: current Lite applies runs directly,
  without a confirmation-preview step. Stop if it returns false.

Legacy action-level `configuration` and `multiple` declarations are rejected.
The plugin owns its action list; store its definitions in table plugin configuration.

## Settings and authenticated connections

Manifest `settings` declares scalar string, boolean, or number preferences.
The host renders these settings; `ctx.settings` provides get/update/reset/observe.
For per-table configuration use `table.pluginConfig` or the bound Eidos file API.

Declare named `connections` for authenticated requests:

```json
{
  "connections": {
    "service": {
      "title": "My service",
      "url": "https://api.example.com/endpoint",
      "configurable": true
    }
  }
}
```

The host handles connection configuration and credentials. The plugin sends a
JSON body through the bound Eidos file or table action's `connections.request`.
Do not put secrets in source, logs, record data, or portable table settings.
Use `browser.networkOrigins` for the separate anonymous `ctx.network.read` API.

## Build a standalone Eidos Lite theme

```sh
npx @eidos.space/plugin-tools create my-theme --template theme
cd my-theme
npm install
npm run check -- --target lite
npm run pack:plugin
```

Edit `plugin.json` to set `kind: "theme"`, `requires.pluginApi: "1.6.0"`, and
the `theme.light` and `theme.dark` token maps. The starter already includes
these fields. Tokens such as `--theme-surface`, `--theme-ink`, `--theme-accent`,
`--lite-sidebar`, `--font-ui`, and `--control-radius` affect the **Eidos Lite
interface**, across all Spaces. The current appearance preference still picks
the light or dark map. See the [specification](https://github.com/mayneyao/eidos/blob/main/docs/specs/eidos-lite-plugins-1.0.md)
for the complete token allowlist and value bounds.

Optional local fonts use `theme.fonts`, for example
`{ "family": "My Sans", "source": "./fonts/my-sans.woff2", "weight": "400" }`.
Packing embeds the font bytes; remote fonts and arbitrary CSS are rejected.
Theme packages have no JavaScript modules, Views, Actions, grants, or runtime
access to files. The generated `.eidos-plugin` can be installed by file picker
or drag and drop. In Plugin Manager, open its detail page and click **Apply
theme**. **Use default theme** clears the selection. Installation alone does
not apply a theme. CLI Serve does not support theme plugins.

## Styling an ordinary plugin and lifecycle

Use the injected `--eidos-*` tokens: background, foreground, border, accent,
muted, surface-hover, surface-selected, font-family, color-scheme, and scrollbar-thumb
(with hover/active variants). Starters include theme-aware CSS.

```css
:root {
  color-scheme: var(--eidos-color-scheme, light);
  font-family: var(--eidos-font-family, system-ui);
  background: var(--eidos-background);
  color: var(--eidos-foreground);
}
* {
  scrollbar-color: var(--eidos-scrollbar-thumb) transparent;
}
```

Register subscriptions for cleanup, honor abort signals, and discard late async
responses after navigation. Use textContent for data-derived text.

## Debug and test

1. Run `npm run check -- --json` for source diagnostics.
2. Load `plugin.json` through Lite's **Load development source** and enable it
   in a test Space. Source edits reload; declaration changes require review.
3. Read the host error banner for loading/permission errors. Where developer
   tools are available, inspect the plugin iframe console and source-mapped stack.
   Catch event-handler promise failures and display useful errors in the plugin UI.
4. Development reloads do not update the installed archive. Package and install
   to test restart behavior. `plugin dev` currently reports that authoring
   sessions are unavailable; it is not a standalone preview server.

The table-action starter includes `npm test` with a small mock context for paging,
cancellation and schema changes. Test the real host separately: one row, explicit
selection, all filtered records, concurrent edits, cancellation, partial failure,
undo/redo, reload, and dark mode. There is no complete mock-host package yet.

## Prepare a release

```sh
npm run pack:plugin
npx @eidos.space/plugin-tools registry dist/local.my-plugin-0.1.0.eidos-plugin --repo owner/repository --category automation --description "Describe the user benefit" --compatibility "Requires Eidos Lite 0.17.0 or later."
```

Packing writes the archive and an adjacent `.sha256` file. The registry helper
hashes the exact archive and prints a submission draft with ID, name, category,
repository, version, tag, asset, checksum and compatibility. Supply a truthful
description and host requirements; adjust the default `v<version>` tag if needed.
The deprecated `preview: false` field remains for registry compatibility.

Upload the immutable archive to GitHub Releases, then submit the entry to
[eidos-space/registry](https://github.com/eidos-space/registry).
The helper does not upload files, publish a release, or open a PR.
