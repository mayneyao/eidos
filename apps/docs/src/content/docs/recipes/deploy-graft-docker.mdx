---
title: Deploy Graft with Docker
---

Run your own Sync server for Eidos Lite. Follow these steps on a Linux server to
get an HTTPS address you can connect to from Lite.

Use **local disk** for the simplest setup, or **Cloudflare R2** to store objects in
a private bucket. Both options need persistent disk space on your server.

## Before you start

You need a Linux AMD64 or ARM64 server with:

- [Docker Engine and Compose v2](https://docs.docker.com/engine/install/).
- Bash, curl and OpenSSL. Run the commands below in Bash as a user who can run Docker.
- A domain pointing to the server, such as `sync.example.com`.
- Ports 80 and 443 accessible from the internet, and [Caddy installed as a system service](https://caddyserver.com/docs/install) on the host.

Replace `sync.example.com` throughout this guide with your domain.

## 1. Download the deployment file

Create a new, private installation directory:

```bash
mkdir -m 700 ~/graft-sync
cd ~/graft-sync
curl -fL --retry 3 -o compose.yaml \
  https://github.com/eidos-space/graft/releases/download/graft-docker-v0.1.1/compose.yaml
```

The file uses the public [Graft Docker 0.1.1 release](https://github.com/eidos-space/graft/releases/tag/graft-docker-v0.1.1)
and pins the image by digest. No GitHub login, source checkout or local build is needed.
Run all later Compose commands from this directory.

## 2. Create the server access key

Run this once for a new installation:

```bash
mkdir -m 700 secrets
(umask 077; openssl rand -hex 32 > secrets/access-key)
chmod 444 secrets/access-key
```

Save the key in your password manager. It grants access to **all Spaces on this
server** and is separate from a Space's encryption password.

The private directories protect the key on the host. The file must be readable
by the container's unprivileged user. Do not repeat the key generation command
on an existing installation: it would replace the key.

## 3. Choose storage

Complete **one** option before starting the server.

### Option A: Local disk

Create `.env` with your public address:

```bash
cat > .env <<'EOF'
GRAFT_PUBLIC_ORIGIN=https://sync.example.com
EOF
```

Docker will create a persistent data volume. Continue to step 4.

### Option B: Cloudflare R2

1. Create a private R2 bucket in your Cloudflare account.
2. Copy its **S3 API endpoint** from the bucket configuration.
3. [Create R2 S3 credentials](https://developers.cloudflare.com/r2/api/tokens/) with **Object Read & Write** permission limited to this bucket. Save the **Access Key ID** and **Secret Access Key**.

These are S3 credentials, not a general Cloudflare API token. The bucket does not
need a public URL. For a jurisdiction-restricted bucket, use the endpoint shown
in its configuration.

Download the additional Compose file:

```bash
curl -fL --retry 3 -o compose.s3.yaml \
  https://github.com/eidos-space/graft/releases/download/graft-docker-v0.1.1/compose.s3.yaml
```

Paste each credential when prompted. Input is hidden and does not enter shell history:

```bash
read -r -s -p 'R2 Access Key ID: ' graft_s3_key_id; printf '\n'
(umask 077; printf '%s' "$graft_s3_key_id" > secrets/s3-access-key-id)
unset graft_s3_key_id
read -r -s -p 'R2 Secret Access Key: ' graft_s3_secret; printf '\n'
(umask 077; printf '%s' "$graft_s3_secret" > secrets/s3-secret-access-key)
unset graft_s3_secret
chmod 444 secrets/s3-access-key-id secrets/s3-secret-access-key
```

Create `.env`, replacing the domain, endpoint and bucket name:

```bash
cat > .env <<'EOF'
COMPOSE_FILE=compose.yaml:compose.s3.yaml
GRAFT_PUBLIC_ORIGIN=https://sync.example.com
GRAFT_S3_ENDPOINT=https://YOUR_ACCOUNT_ID.r2.cloudflarestorage.com
GRAFT_S3_REGION=auto
GRAFT_S3_BUCKET=your-private-bucket
GRAFT_S3_PREFIX=graft/
GRAFT_S3_FORCE_PATH_STYLE=true
EOF
```

R2 uses [region `auto`](https://developers.cloudflare.com/r2/api/s3/api/).
Use a dedicated bucket or a prefix reserved for this installation, ending in `/`.
`COMPOSE_FILE` makes the commands below load both Compose files automatically.

R2 stores objects, but the Docker volume still holds metadata and unfinished
uploads. Reserve disk space for upload parts and an assembled copy of each upload
being completed.

## 4. Start the server

```bash
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
curl --fail --show-error --silent --retry 10 --retry-all-errors --retry-delay 2 \
  http://127.0.0.1:8787/healthz
```

The last command should return a successful health response. If it fails, check
the logs before continuing:

```bash
docker compose logs --tail=100 graft
```

The container only listens on `127.0.0.1:8787`; Caddy will provide public access.

## 5. Enable HTTPS

Add this block to `/etc/caddy/Caddyfile` on the host, preserving existing sites:

```text
sync.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

Validate and reload Caddy:

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
curl -fsS https://sync.example.com/healthz
```

Wait for the public health check to succeed before connecting Lite. For certificate
errors, check DNS and whether ports 80 and 443 reach Caddy.

Using another proxy? Allow request bodies of at least 64 MiB and transfers of at
least 120 seconds. Forward paths and authorization headers unchanged and disable
API caching. A containerized proxy needs a shared Docker network with upstream
`graft:8787`, rather than the host-loopback configuration above.

## 6. Connect Lite

Display the server key:

```bash
cat secrets/access-key
```

Follow [Connect a self-hosted server](/recipes/sync-custom-server/) in Lite.
Use `https://sync.example.com` as the address and paste the key.
Also keep your Space's sync password safe: the server key cannot replace it.

Once connected, add a record and a small attachment. Download the Space on another
computer and open both, then edit a record there and confirm the first computer
receives the change. This checks synchronization beyond the server health check.

Initial connection confirms that uploaded data is stored. This server version
does not require Lite to download the entire upload for confirmation, though
the server still reads stored objects. Older servers may require a full download.
If confirmation fails, keep your local Space and retry after fixing the problem.

## Maintain the installation

### Stop and restart

Run from `~/graft-sync`:

```bash
docker compose stop
docker compose start
```

Keep the deployment directory and its Docker data volume. **Do not use
`docker compose down -v` unless you intend to delete the server's local data.**
Run one Graft instance per data volume.

### Back up and upgrade

Pause synchronization and stop the container before backing up:

- **Local storage:** copy the complete `/data` volume.
- **R2 or other S3 storage:** copy both `/data` and the matching bucket objects
  while the server is stopped. Neither copy alone is sufficient.
- Securely back up the Compose files, `.env` and access keys. Keep Space sync passwords separately.

Restart after the backup. Test restoration into a separate empty volume and
check a client download before relying on a backup. R2 is not a backup by itself:
deleting an object removes its current copy.

To upgrade, back up first. Download the new release's Compose files into a
temporary directory and compare them with your installation. Update the image
reference and required settings, preserving your `.env`, secrets and data volume.
Then run:

```bash
docker compose pull
docker compose up -d
curl -fsS https://sync.example.com/healthz
```

Check synchronization in Lite before discarding the previous image and backup.

### Other S3 providers and storage changes

Changing storage mode, endpoint, bucket or prefix does **not** migrate data.
For an existing installation, deploy a separate server with fresh storage and
use Lite's **Switch server** flow.

For a new installation with another S3 provider, follow option B using that
provider's HTTPS endpoint, region and credentials. For Backblaze B2, copy the
endpoint and region from your bucket details and create a bucket-restricted
[application key](https://www.backblaze.com/docs/cloud-storage-application-keys).
Save `keyID` in `secrets/s3-access-key-id` and `applicationKey` in
`secrets/s3-secret-access-key`.

Credentials need bucket access, object reads/writes/deletes and multipart uploads,
including aborting incomplete uploads. Versioned buckets also need permission to
delete object versions. Object Lock and retention rules can prevent deletion.
Avoid expiration rules on live objects in your installation's prefix.
Provider storage, request and transfer charges apply.

This release was tested with local storage, MinIO and Cloudflare R2. The B2
configuration uses its S3 API but has not been tested against a live B2 bucket.

## Troubleshooting

| Symptom                             | Check                                                                                                             |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Compose reports missing variables   | Check `.env` in the deployment directory; R2 requires all option B fields.                                        |
| Local health check fails            | Run `docker compose ps` and `docker compose logs --tail=100 graft`. Check secret permissions and free disk space. |
| Public health check fails           | Check DNS, firewall ports and Caddy configuration.                                                                |
| Lite reports an authorization error | Use the server key, not the Space password or R2 credentials.                                                     |
| R2 transfers fail                   | Check the S3 endpoint, bucket name and bucket-scoped Object Read & Write credentials.                             |
