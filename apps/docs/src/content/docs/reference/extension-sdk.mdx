`@eidos.space/extension-sdk` is the supported TypeScript contract for
third-party file-based extensions. It does not expose the legacy `DataSpace`
object, Electron, Node.js, SQLite, or raw filesystem APIs.

The SDK is currently an experimental developer preview. Version 1 includes a
worker context for commands and a separate UI context for text file editors.
Storage, secrets, network access, Eidos File views, and agent tools remain outside the
executable boundary.

SDK imports are type-only in extension source. The fixed compiler removes them
and rejects arbitrary bare-module imports; the host constructs the runtime
context itself.

## Worker context

```ts
import type { ExtensionContext } from "@eidos.space/extension-sdk"

export function activate(context: ExtensionContext) {
  context.subscriptions.add(
    context.commands.register("example.package.command", async (resource) => {
      const text = await context.space.files.readText(resource.path)
      context.window.showNotice(`${text.length} characters`)
    })
  )
}
```

| Namespace               | Current operations                              | Enforcement                                            |
| ----------------------- | ----------------------------------------------- | ------------------------------------------------------ |
| `context.commands`      | Register a command declared by the same package | Unknown IDs fail activation                            |
| `context.space.files`   | `readText(path)`                                | Requires an active matching `files.read` grant         |
| `context.window`        | `showNotice`, `confirm`, `select`               | Host validates and renders semantic UI                 |
| `context.subscriptions` | Own disposables                                 | Disposed on stop, update, disable, or stale generation |

Worker `activate()` is lazy. Installing or discovering a package does not start
it. A worker is tied to the inspected content digest and effective grants;
changing either terminates the old generation.

## File editor context

A package with `entrypoints.ui` and a matching `fileEditors` contribution
exports:

```ts
import type { ExtensionFileEditorContext } from "@eidos.space/extension-sdk"

export function activate(context: ExtensionFileEditorContext) {
  context.root.textContent = context.document.snapshot.text
}
```

| Member                              | Meaning                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------ |
| `extensionId`, `editorId`, `viewId` | Stable activation identity and this surface instance                     |
| `root`                              | The only DOM mount point provided to the package                         |
| `document.snapshot`                 | Latest immutable text, resource metadata, revision, dirty and undo state |
| `document.applyEdits()`             | Submit sorted, non-overlapping UTF-16 edits against the current revision |
| `document.save()`                   | Ask the host to persist the current revision                             |
| `document.undo()` / `redo()`        | Operate on shared host-owned document history                            |
| `document.resync()`                 | Request a fresh full snapshot after a stale local view                   |
| `document.onDidChange()`            | Receive minimal edits or a replacement snapshot from every view          |
| `document.onDidChangeState()`       | Receive dirty, saved baseline, conflict, and undo-state changes          |
| `document.onDidChangeSaveState()`   | Receive saving, saved, and error transitions                             |
| `appearance.current`                | Resolved locale, color scheme, and stable theme tokens                   |
| `capabilities`                      | Effective editable/save/undo and autosave policy, after local grants     |
| `subscriptions`                     | Listeners the host disposes with the surface generation                  |

The document API returns the accepted revision number. It never returns a file
handle. A surface must apply every host broadcast, including edits attributed
to its own view, because the host is authoritative.

The exact serializable messages are defined by the
[surface protocol](/reference/extension-surface-protocol/).

## Appearance tokens

The runtime maps `appearance.current.theme` to CSS custom properties:

```css
var(--eidos-color-background)
var(--eidos-color-foreground)
var(--eidos-color-muted-background)
var(--eidos-color-muted-foreground)
var(--eidos-color-border)
var(--eidos-color-accent)
var(--eidos-color-accent-foreground)
var(--eidos-color-destructive)
var(--eidos-color-destructive-foreground)
var(--eidos-color-focus-ring)
var(--eidos-font-family)
var(--eidos-font-family-mono)
```

These values are resolved host tokens, not class names. The host updates them
when appearance changes, so a surface does not need access to Eidos internals.

## Error contracts

Worker failures use codes such as `CAPABILITY_DENIED`, `RUNTIME_STALE`,
`RUNTIME_TIMEOUT`, and `RUNTIME_COMMAND_FAILED`.

File-editor document requests may reject with `INVALID_EDIT`,
`STALE_REVISION`, `READ_ONLY`, `CONFLICT`, `RUNTIME_STALE`, `SAVE_FAILED`, or
`NOT_AVAILABLE`. Treat these as runtime state, not as reasons to bypass the SDK.
After `STALE_REVISION`, apply pending broadcasts or call `resync()` before
retrying.
