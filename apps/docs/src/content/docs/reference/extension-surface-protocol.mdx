`@eidos.space/extension-surface-protocol` is the transport and document-state
contract for custom extension UI. It contains no React, Electron, iframe,
filesystem, or editor implementation. P3a of the file-based extension RFC is
implemented in this package; activating third-party UI entrypoints in Desktop
is still preview work.

## Fixed version 1 invariants

| Invariant         | Version 1 rule                                                             |
| ----------------- | -------------------------------------------------------------------------- |
| Offset unit       | JavaScript UTF-16 code units, not Unicode code points or UTF-8 bytes       |
| Revision          | Positive, monotonic integer owned by the host                              |
| Edit base         | Every edit in one batch targets the same exact `baseRevision`              |
| Document owner    | The host owns text, dirty state, undo/redo, save, and conflicts            |
| Surface authority | A surface may request bounded edits; it cannot write a file directly       |
| Save              | Host-internal, single-use compare-and-swap token                           |
| Multiple views    | One document model broadcasts accepted edits to every attached view        |
| Conflict choice   | Reload or overwrite is chosen by host UI, never silently by extension code |

Protocol constants are deliberately small for the first editable surface:

- at most 128 edits in one batch;
- at most 256 Ki UTF-16 code units inserted;
- at most 256 Ki UTF-16 code units changed, counting inserted and removed text;
- at most 512 Ki UTF-16 code units in one text document.

Callers may lower these limits. They cannot raise the fixed version 1 limits.
Larger documents fall back to a native text preview until a streaming contract
exists.

## Connection and capability negotiation

The host transfers a dedicated `MessagePort` to one sandboxed surface. After
the surface sends `ready`, the host sends one `initialize` message containing:

- `protocolVersion`;
- immutable package `generation`;
- `editorId` and unique `viewId`;
- a complete initial document snapshot;
- capabilities such as `editable`, `save`, `undoRedo`, and `savePolicy`.

The surface must not infer a capability from its own manifest. For example, it
must render read-only UI when `editable` is false even if the package requested
write access. An unsupported protocol version closes the port and Eidos falls
back to another compatible or native editor.

Only the bootstrap transfers the port through `window.postMessage`. Document
traffic stays on that port. A surface never receives an Electron bridge, host
DOM, raw filesystem handle, SQLite connection, or unrestricted network client.

## Apply one edit

Suppose revision 7 contains this Markdown:

```md
- [ ] Ship surface protocol
```

Checking the task changes one UTF-16 code unit. The surface sends:

```ts
port.postMessage({
  type: "apply-edits",
  requestId: "edit-42",
  documentId: snapshot.documentId,
  baseRevision: 7,
  edits: [{ start: 3, end: 4, text: "x" }],
})
```

The host parses the unknown message, validates every bound, applies it only if
revision 7 is still current, records the inverse edit for undo, advances to
revision 8, and broadcasts `document-changed` to all views. A second view still
submitting against revision 7 receives `STALE_REVISION` and requests a full
`resync`; the host never guesses how to merge stale offsets.

## Undo, redo, and multiple views

Undo and redo are document operations, not iframe-local history. A request from
one view changes the shared revision and produces minimal edits that every view
applies. A surface may keep transient UI state such as selection and filters,
but it cannot claim that document content is dirty or saved.

The broadcast includes `originViewId`. This is attribution, not permission to
ignore the update: the origin view must also advance to the broadcast revision.

## Save and external changes

`request-save` asks the host to save the current revision. Internally, the host
document model issues a bounded, single-use token containing the exact text and
the persisted content digest it was based on. The filesystem writer must still
observe that digest before replacing the file.

An older save may finish after a newer edit. In that case its revision becomes
the saved baseline while the newer text remains dirty; it never replaces the
newer in-memory document. Replayed, altered, cancelled, or excess in-flight
tokens are rejected.

When file watching observes a new digest:

1. A clean document reloads the external snapshot, clears history, and
   broadcasts `document-replaced`.
2. A dirty document enters `externalConflict`; save is blocked.
3. Host UI asks the user to **Reload** or **Overwrite**.
4. Reload accepts external text. Overwrite keeps local text but changes the
   compare-and-swap baseline to the newly observed external digest.

The extension cannot dismiss or resolve this conflict itself.

## Surface-to-host requests

| Message                         | Purpose                                               |
| ------------------------------- | ----------------------------------------------------- |
| `ready`                         | Complete protocol handshake                           |
| `apply-edits`                   | Submit one bounded batch against an exact revision    |
| `request-save`                  | Ask the host to persist the current revision          |
| `request-undo` / `request-redo` | Operate on shared document history                    |
| `request-resync`                | Replace local surface state with a full host snapshot |
| `closed`                        | Tell the host the surface has disposed itself         |

Every request receives a `request-result`. Stable failure codes include
`INVALID_EDIT`, `STALE_REVISION`, `READ_ONLY`, `CONFLICT`, `RUNTIME_STALE`, and
`NOT_AVAILABLE`. Protocol errors are data; malformed surface messages must not
crash the host process.

## Author checklist

- Parse the initial snapshot without rewriting it.
- Use UTF-16 offsets from JavaScript strings.
- Submit minimal edits against the last accepted revision.
- Apply every host broadcast, including broadcasts attributed to this view.
- Request resync after `STALE_REVISION`.
- Derive save/undo/dirty UI only from host state.
- Disable unavailable capabilities instead of polyfilling direct file access.
- Dispose listeners and the port when the surface closes.

The first proof surface will be an editable Markdown Task Board. It will toggle
checkbox markers through this protocol while Eidos retains normal file save,
undo, external-change, and Graft behavior.
