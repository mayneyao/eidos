`@eidos.space/base-ui` is intended to be the reusable React editor for the open
`.base` format. Use it when your application needs Eidos-compatible tables and
views without embedding the Eidos Desktop application.

:::caution[This page defines the target public API]
The package already exposes the shared Grid, Gallery, Kanban, data-source, and
renderer implementations, but the opt-in plugin factories shown below are not
implemented yet. The examples describe the package boundary we intend to make
stable before publishing a supported release. See [Current API and migration](#current-api-and-migration)
for what can be used today.
:::

## Choose what your editor supports

The default package should provide a complete Grid editor. Other view types are
explicit additions:

| Product you want          | Imports you add                                   |
| ------------------------- | ------------------------------------------------- |
| Grid-only Base editor     | `@eidos.space/base-ui`                            |
| Grid and Gallery          | `@eidos.space/base-ui/gallery`                    |
| Grid and Kanban           | `@eidos.space/base-ui/kanban`                     |
| Grid, Gallery, and Kanban | Both optional view modules                        |
| Grid and your own view    | `@eidos.space/base-ui/view-api` and your renderer |

Importing the root package must not register optional views globally. Importing
Gallery must not pull Kanban into the application bundle, and importing Kanban
must not require the Gallery plugin. Shared card primitives may be deduplicated
internally without changing this consumer contract.

## Start with Grid

Install the runtime contract and the UI package. React, React DOM, and Glide Data
Grid remain peer dependencies so your application controls their versions.

```sh
pnpm add @eidos.space/base @eidos.space/base-ui \
  @glideapps/glide-data-grid react react-dom
```

Import the shared styles once at your application entry point:

```ts
import "@eidos.space/base-ui/styles.css"
```

Then provide a worker-backed `BaseEditorDataSource` and render the editor. Grid
is available without a view plugin:

```tsx
import {
  BaseEditor,
  BaseUIProvider,
  type BaseEditorDataSource,
} from "@eidos.space/base-ui"

export function TasksBase({ source }: { source: BaseEditorDataSource }) {
  return (
    <BaseUIProvider
      themeName="light"
      locale="en-US"
      resolveAssetUrl={(path) => `/files/${encodeURIComponent(path)}`}
    >
      <BaseEditor
        source={source}
        tableId="tasks"
        onError={(error) => console.error(error)}
      />
    </BaseUIProvider>
  )
}
```

`BaseEditor` should open the table's first saved view unless `viewId` is passed.
If that view type is unavailable, it should show an unsupported-view state and
let the user choose a supported view. It must never rewrite the saved view to
Grid as a fallback.

`locale` is a target provider option. English and Simplified Chinese should be
supported by the package; hosts may supply additional message catalogs without
forking a renderer.

## Add Gallery

Add Gallery at the application boundary. The saved view still comes from the
`.base` file; the plugin supplies the React implementation for `type="gallery"`.

```tsx
import { BaseEditor } from "@eidos.space/base-ui"
import { galleryView } from "@eidos.space/base-ui/gallery"
import "@eidos.space/base-ui/gallery/styles.css"

const viewPlugins = [galleryView()]

export function TasksBase({ source }) {
  return (
    <BaseEditor source={source} tableId="tasks" viewPlugins={viewPlugins} />
  )
}
```

`galleryView()` should read card size, cover, visible fields, and other saved
settings from the view metadata. Application-level behavior—opening a record,
resolving an asset, reporting an error—belongs to `BaseEditor` or
`BaseUIProvider`, not to the `.base` file.

If a file contains a Gallery view but the host did not import `galleryView`, the
host should explain that Gallery is unavailable. The data and view metadata
remain intact.

## Add Kanban

Kanban follows the same pattern:

```tsx
import { BaseEditor } from "@eidos.space/base-ui"
import { kanbanView } from "@eidos.space/base-ui/kanban"
import "@eidos.space/base-ui/kanban/styles.css"

const viewPlugins = [kanbanView()]

export function TasksBase({ source }) {
  return (
    <BaseEditor source={source} tableId="tasks" viewPlugins={viewPlugins} />
  )
}
```

Kanban requires runtime group counts in addition to paged rows. Registering the
plugin is not enough if the host adapter omits that capability. The editor
should report the missing capability instead of loading the whole table and
grouping it on the React thread.

To support both optional views, pass both plugins:

```ts
import { galleryView } from "@eidos.space/base-ui/gallery"
import { kanbanView } from "@eidos.space/base-ui/kanban"

const viewPlugins = [galleryView(), kanbanView()]
```

Plugin order must not change saved-view behavior. Registering the same type
twice should fail during development rather than silently selecting one.

## Supply data without coupling UI to SQLite

Every view reads and writes through `BaseEditorDataSource`. Your browser,
Electron app, or native wrapper owns the worker and file lifecycle; Base UI owns
React behavior.

```ts
const source: BaseEditorDataSource = {
  getSnapshot: () => worker.call({ type: "snapshot" }),
  getPage: (tableId, offset, limit, query, totalHint, cursor, projection) =>
    worker.call({
      type: "page",
      tableId,
      offset,
      limit,
      query,
      totalHint,
      cursor,
      projection,
    }),
  getRow: (tableId, rowId) => worker.call({ type: "row", tableId, rowId }),
  getGroupCounts: (tableId, columnName, query) =>
    worker.call({ type: "group-counts", tableId, columnName, query }),
  insertRow: (tableId, row) =>
    worker.call({ type: "insert-row", tableId, row }),
  updateRow: (tableId, rowId, changes) =>
    worker.call({ type: "update-row", tableId, rowId, changes }),
}
```

The adapter must call `@eidos.space/base` for validation, queries, grouping,
migrations, and mutations. A UI plugin must not compile filters into SQL or
write a SQLite file directly.

### Capability matrix

| View    | Required data-source capabilities                                 |
| ------- | ----------------------------------------------------------------- |
| Grid    | Snapshot, paged rows, row update; field/view mutations as enabled |
| Gallery | Grid row access, cursor paging, projection, full-row inspection   |
| Kanban  | Gallery row access, group counts, per-group paging, row insert    |

The editor should determine support before mounting a renderer. A read-only
source may mount a plugin with mutation actions disabled; a source missing a
required read capability may not mount it.

## Publish your own view plugin

A custom view plugin connects a persisted `view.type` to a React renderer. It
does not create a second schema or query language.

The target helper is `defineBaseView`:

```tsx
import { defineBaseView } from "@eidos.space/base-ui/view-api"

interface TimelineProperties {
  startField: string
  endField?: string
  zoom?: "day" | "week" | "month"
}

export const timelineView = defineBaseView<TimelineProperties>({
  type: "acme.timeline",
  displayName: "Timeline",
  requiredCapabilities: ["page", "updateRow"],
  parseProperties(value) {
    if (
      !value ||
      typeof value !== "object" ||
      typeof (value as Record<string, unknown>).startField !== "string"
    ) {
      throw new Error("Timeline needs a start field")
    }
    return value as TimelineProperties
  },
  Renderer: TimelineRenderer,
  PropertyEditor: TimelinePropertyEditor,
})
```

Register it like a built-in optional view:

```tsx
<BaseEditor source={source} tableId="tasks" viewPlugins={[timelineView]} />
```

A public plugin should own:

- a stable, preferably namespaced view `type`;
- property parsing and a user-facing invalid-configuration state;
- the renderer and, when needed, its property editor;
- a declaration of the data-source capabilities it requires;
- its styles and localization messages;
- tests for paging, mutation failure, read-only mode, keyboard access, and
  unknown property preservation.

It should not own migrations, SQL generation, file handles, save state,
conflict resolution, or Base metadata tables. Those remain runtime and host
responsibilities.

## What the host still owns

Base UI is an editor surface, not a file manager. The embedding application
continues to own:

- opening a `.base` file and constructing the runtime worker;
- dirty, saving, saved, error, and conflict states;
- recovery, Save As, external-change detection, and write-back;
- current theme and locale;
- asset URLs, file previews, and record navigation;
- permission prompts and read-only policy.

This separation lets a browser editor, a Desktop application, and another
vendor's product use the same view implementations without sharing their file
access code.

## Package guarantees before a stable release

The publishable package should meet these conditions:

1. The root export contains the editor shell, shared contracts, and default
   Grid only.
2. Gallery and Kanban use stable subpath exports and can be omitted from the
   JavaScript and CSS bundle.
3. No public module imports from `apps/web-app` or `apps/desktop`.
4. Every renderer receives runtime-normalized rows and queries; no renderer
   owns Base SQL semantics.
5. Unknown view types and properties round-trip without data loss.
6. Plugin registration is local to an editor instance; importing a module has
   no global side effect.
7. Missing plugins and capabilities produce actionable UI, not silent fallback.
8. Public types, styles, peer dependencies, and browser requirements follow
   semantic versioning.

## Current API and migration

The current `0.1` package exposes the lower-level pieces used by Eidos Desktop
and Base Web:

```tsx
import {
  BaseEditorView,
  BaseUIProvider,
  type BaseViewRendererRegistry,
} from "@eidos.space/base-ui"
```

`BaseEditorView` accepts a selected table, selected view, data source, and a
renderer registry. Gallery and Kanban also have public component subpaths. This
is enough for trusted application integrations, but the current root view
router still imports all built-in renderers and therefore does not provide the
opt-in bundle boundary described above.

The proposed migration keeps the lower-level renderer contract and adds:

| Proposed API           | Purpose                                      |
| ---------------------- | -------------------------------------------- |
| `BaseEditor`           | High-level table/view editor with Grid       |
| `galleryView()`        | Opt-in Gallery plugin                        |
| `kanbanView()`         | Opt-in Kanban plugin                         |
| `defineBaseView()`     | Typed third-party plugin definition          |
| `viewPlugins`          | Instance-local registration                  |
| Capability declaration | Fail early when a host adapter is incomplete |
| Per-view style exports | Keep optional CSS out of Grid-only apps      |

For the `.base` metadata and the current low-level renderer example, continue
to [Base format and custom views](/reference/base-custom-views/).

## Trusted plugins and sandboxed extensions

View plugins run React inside the embedding application. Install only code you
trust and review it like any other application dependency.

This API is separate from the sandboxed Eidos Extension SDK. A future extension
contribution may use the same data and view concepts, but it must cross an
isolated capability bridge instead of receiving `BaseEditorDataSource` or host
React access directly.
