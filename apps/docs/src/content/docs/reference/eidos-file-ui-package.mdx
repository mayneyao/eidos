`@eidos.space/eidos-file-ui` is the published React editing surface for the open
`.eidos` format. It contains the shared Grid, Gallery, Kanban, query controls,
field editors, record inspector, and editor chrome used by Eidos applications.

The UI package never opens a SQLite database. It reads and writes through an
`EidosFileEditorDataSource`, so browser Workers, Electron IPC, and native hosts
can use the same components without moving SQL work onto the React thread.

## Install

```sh
pnpm add @eidos.space/eidos-file @eidos.space/eidos-file-ui \
  @glideapps/glide-data-grid react react-dom
```

Import the shared styles once at the application entry point:

```ts
import "@eidos.space/eidos-file-ui/styles.css"
```

## Package responsibilities

| Layer                        | Owns                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `@eidos.space/eidos-file`    | Format validation, metadata, queries, mutations, Formula, Lookup, relations, and CSV                       |
| `@eidos.space/eidos-file-ui` | React rendering, keyboard interaction, selection, field controls, inspectors, and view routing             |
| Host application             | File handles, Worker/IPC, permissions, dirty/save/recovery state, conflicts, theme, locale, and asset URLs |

Do not copy format rules into a renderer. The runtime is the only layer that
interprets Eidos File schema and compiles structured queries into SQL.

## Render an Eidos File view

`EidosFileEditorView` routes the selected saved view to Grid, Gallery, Kanban,
or a host-registered renderer:

```tsx
import type {
  EidosFileTableSnapshot,
  EidosFileViewInfo,
} from "@eidos.space/eidos-file"
import {
  EidosFileEditorView,
  EidosFileUIProvider,
  type EidosFileEditorDataSource,
} from "@eidos.space/eidos-file-ui"
import "@eidos.space/eidos-file-ui/styles.css"

export function ProjectView({
  source,
  table,
  view,
}: {
  source: EidosFileEditorDataSource
  table: EidosFileTableSnapshot
  view: EidosFileViewInfo
}) {
  return (
    <EidosFileUIProvider
      themeName="light"
      resolveAssetUrl={(path) => `/files/${encodeURIComponent(path)}`}
    >
      <EidosFileEditorView
        source={source}
        table={table}
        view={view}
        onMutation={() => markDocumentDirty()}
        onError={(error) => reportEditorError(error)}
      />
    </EidosFileUIProvider>
  )
}
```

The package includes built-in renderers for persisted `grid`, `gallery`, and
`kanban` view types. Unknown view types remain intact in the file and render an
unsupported-view state until the host registers a matching renderer.

The component must fill a container with an explicit height. Built-in views
virtualize rows and cards inside that container.

## Supply the data source

The asynchronous data source is the UI boundary. A typical implementation
forwards each method to one semantic Worker or IPC request:

```ts
const source: EidosFileEditorDataSource = {
  getSnapshot: () => worker.call({ type: "snapshot" }),
  getPage: (tableId, offset, limit, query, totalHint, cursor, projection) =>
    worker.call({
      type: "page",
      tableId,
      offset,
      limit,
      query,
      totalHint,
      cursor,
      projection,
    }),
  getRow: (tableId, rowId) => worker.call({ type: "row", tableId, rowId }),
  getGroupCounts: (tableId, columnName, query) =>
    worker.call({ type: "group-counts", tableId, columnName, query }),
  insertRow: (tableId, row) =>
    worker.call({ type: "insert-row", tableId, row }),
  updateRow: (tableId, rowId, changes) =>
    worker.call({ type: "update-row", tableId, rowId, changes }),
  updateField: (tableId, columnName, changes) =>
    worker.call({ type: "update-field", tableId, columnName, changes }),
  addField: (tableId, field, placement) =>
    worker.call({ type: "add-field", tableId, field, placement }),
  deleteField: (tableId, columnName) =>
    worker.call({ type: "delete-field", tableId, columnName }),
  updateView: (viewId, changes) =>
    worker.call({ type: "update-view", viewId, changes }),
}
```

The Worker calls `@eidos.space/eidos-file`. A renderer must not execute SQL,
scan the entire table to filter or group rows, or reinterpret cell encodings.

`getRow` powers complete record inspectors. `getGroupCounts` powers Kanban
without downloading every record. Implement both for the complete built-in
experience.

## Compose the editor chrome

Hosts that need the complete Desktop-style layout can compose the published
shell primitives around `EidosFileEditorView`:

```tsx
import {
  EidosFileEditorContent,
  EidosFileEditorRoot,
  EidosFileEditorView,
  EidosFileEditorWorkbar,
  EidosFileQueryToolbar,
  EidosFileSheetTabStrip,
  EidosFileViewTabStrip,
} from "@eidos.space/eidos-file-ui"
```

The host owns active table and view selection. Persist filters, sorts, and view
properties with `source.updateView`; keep transient search, focus, and open-menu
state in React.

Low-level built-ins are also available when an application intentionally owns
the surrounding shell:

```ts
import { EidosFileDataGrid } from "@eidos.space/eidos-file-ui/eidos-file-data-grid"
import { EidosFileGalleryView } from "@eidos.space/eidos-file-ui/eidos-file-gallery-view"
import { EidosFileKanbanView } from "@eidos.space/eidos-file-ui/eidos-file-kanban-view"
```

## Register a custom view

Pass an instance-local renderer registry. A namespaced key should match the
`eidos__views.type` value stored in the file:

```tsx
import {
  EidosFileEditorView,
  builtInEidosFileViewRenderers,
} from "@eidos.space/eidos-file-ui"
import { TimelineView } from "@example/eidos-file-timeline-view"

const renderers = {
  ...builtInEidosFileViewRenderers,
  "com.example.timeline": TimelineView,
}

<EidosFileEditorView
  source={source}
  table={table}
  view={view}
  renderers={renderers}
/>
```

The registry controls rendering only. Creating a saved view remains a runtime
operation, and its `properties` must contain portable JSON values. Read
[Eidos File format and custom views](/reference/eidos-file-custom-views/) for
the complete renderer contract.

## Host checklist

- Keep SQLite and expensive queries in a Worker or background process.
- Page large tables and pass projections for card-style views.
- Mark the document dirty after successful row, field, or view mutations.
- Keep failed saves recoverable and detect external changes before overwrite.
- Disable mutation actions for read-only sources.
- Resolve File fields through host-controlled asset URLs.
- Preserve unknown view types and properties without rewriting them.
- Test keyboard focus, narrow containers, light/dark themes, and large datasets.

View renderers run as trusted React code in the embedding application. The
sandboxed Eidos Extension surface is a separate capability boundary and does
not receive direct host React or SQLite access.
