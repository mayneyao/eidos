Eidos separates discovery, build, and activation. Reading a manifest does not
execute code, and installing source does not make a package active.

```text
discovered
    │ validate manifest + compatibility
    ▼
disabled / untrusted ── user trust + enable + grants ──┐
                                                       ▼
                                               ready to build
                                                       │ trigger
                                                       ▼
                                                activating
                                                  │       │
                                               active   failed
                                                  │
                          content/grant/app change │
                                                  ▼
                                               stopped
```

## Derived activation

Most activation events come from contributions:

- Invoking a command activates its worker.
- Opening a matching file editor activates its UI entrypoint.
- Showing a Base view activates only that view.
- Calling an agent tool activates its tool handler.

Packages cannot request unconditional startup in the first delivery. Explicit
background activation is a privileged capability reserved for a later design.

## Activation contract

```ts
export function activate(context: ExtensionContext): void | Promise<void>
export function deactivate(): void | Promise<void>
```

`context.subscriptions` owns commands, events, timers, and other disposable
resources. The host disposes them even when activation throws or the worker is
terminated.

## Package content changes

Trust is keyed by canonical ID, content digest, and permission hash. Outside an
active development session, when an installed package file other than the
host-managed `extension.lock.json` changes, Eidos:

1. terminates the active worker and closes its capability channel;
2. marks the old build stale;
3. computes a new digest;
4. requires trust for that digest before rebuilding and activating.

Rapid saves use generation tokens. Results from an older build generation are
discarded and can never replace a newer source build.

### Development sessions

During local development, repeatedly trusting every new content digest would
make the normal security rule unusable. Eidos therefore provides an explicit,
Space-bound **Development session**:

1. Trust the exact source snapshot, grant only the capabilities it needs, and
   enable it.
2. Expand the package in **Settings → Extensions** and select **Start
   development**.
3. Edit package files under `.eidos/extensions/<publisher.name>/` with any
   editor. Eidos inspects and compiles the new bytes, disposes the previous
   Worker or UI surface, and reloads only that package.
4. Select **Stop development** before reviewing a permission or package-ID
   change.

The session exists only in Desktop memory. It is anchored to the trusted
snapshot and freezes that snapshot's granted capabilities. A source-only
change can run when the package ID and permission hash remain identical, but
the new digest is **not** written to the trusted-snapshot database. Changing
the package ID or requested permissions blocks execution until the session is
stopped and the new snapshot is reviewed normally.

Invalid TypeScript or manifest edits put the session into **Fix required**.
Fixing the source triggers another bounded build and automatically reopens a
matching file editor. Open dirty documents are saved before reload; a failed
save blocks reload and keeps the previous document session recoverable. App
restart, Space release, watcher failure, uninstall, or update clears the
development session.

## Failure behavior

Activation failures are attached to the package state and shown in the
Extension Manager. A failed package does not disappear, retry forever, or keep
executing a previous bundle silently.
