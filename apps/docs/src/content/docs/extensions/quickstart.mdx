This guide builds **Markdown Task Board**, an extension that opens
`*.tasks.md` files as a two-column board while keeping ordinary Markdown as the
source of truth.

The complete, compiler-checked package is available at
[`apps/docs/examples/markdown-task-board`](https://github.com/mayneyao/eidos/tree/dev/apps/docs/examples/markdown-task-board).

## The user scenario

Create `projects/website.tasks.md`:

```md
# Website launch

- [x] Choose a domain
- [ ] Finish the landing page
- [ ] Invite beta users
```

With the extension enabled, opening this file shows:

- a summary of **2 to do**, **1 completed**, and **33%** progress;
- a **To do** column and a **Completed** column;
- one card for every Markdown task-list item;
- inline save state supplied by Eidos;
- a checkbox interaction that moves a card without changing the file format.

The user can choose **Open with Eidos** from the file context menu at any time
to inspect or edit the raw Markdown in the normal Lexical editor.

## What owns the data

The Task Board owns presentation, not persistence:

```text
website.tasks.md
       │ host opens one versioned TextDocument
       ▼
sandboxed Task Board surface
       │ applyEdits([{ start, end, text: "x" }])
       ▼
Eidos validates the revision and records undo
       │ autosave with digest compare-and-swap
       ▼
website.tasks.md + Graft-visible file change
```

The surface never receives Electron, Node.js, a raw filesystem handle, or a
`writeFile()` function. Eidos owns revisions, dirty state, undo/redo,
autosave, external-change conflicts, and synchronization between multiple
views of the same file.

## Step 1: Create the package

Create this structure outside a production Space while developing:

```text
markdown-task-board/
├── extension.json
└── src/
    ├── editor.css
    ├── editor.ts
    └── tasks.ts
```

Create `extension.json`:

```json
{
  "$schema": "https://docs.eidos.space/schemas/extension-manifest.schema.json",
  "manifestVersion": 1,
  "publisher": "example",
  "name": "markdown-task-board",
  "displayName": "Markdown Task Board",
  "description": "Open *.tasks.md files as an editable task board without changing their Markdown format.",
  "version": "0.1.0",
  "engines": { "eidos": ">=0.33.0" },
  "entrypoints": { "ui": "src/editor.ts" },
  "contributes": {
    "fileEditors": [
      {
        "id": "example.markdown-task-board.editor",
        "displayName": "Task Board",
        "selector": [
          {
            "filenamePattern": "**/*.tasks.md",
            "mediaType": "text/markdown"
          }
        ],
        "priority": "default"
      }
    ]
  },
  "permissions": {
    "files": {
      "read": ["**/*.tasks.md"],
      "write": ["**/*.tasks.md"]
    },
    "network": []
  }
}
```

The important decisions are:

| Manifest value        | Effect                                                              |
| --------------------- | ------------------------------------------------------------------- |
| `entrypoints.ui`      | Builds a DOM surface; no worker is needed for this package.         |
| `fileEditors[].id`    | Stable editor identity used in tab URLs and activation.             |
| `**/*.tasks.md`       | Leaves ordinary `.md` files with the built-in editor.               |
| `priority: "default"` | Opens matching files as a board without another picker.             |
| read + write grants   | Lets the host open and persist matching files after local approval. |
| empty `network`       | Makes network APIs unavailable inside the surface.                  |

Changing source or requested permissions changes the inspected snapshot. Trust,
enablement, and grants apply only to the exact content and permission digests
the user reviewed.

## Step 2: Parse Markdown without rewriting it

`src/tasks.ts` scans task-list lines and records the checkbox marker offset:

```ts
export interface MarkdownTask {
  checked: boolean
  label: string
  line: number
  markerOffset: number
}

const TASK_LINE = /^(\s*[-*+]\s+\[)([ xX])\](?:\s+(.*?))?\s*$/
```

The complete parser also ignores fenced code blocks and handles CRLF files. Its
offsets are JavaScript UTF-16 code units, which is the version 1 surface
protocol coordinate system. An emoji before a task therefore does not corrupt
the edit range.

Do not parse the document into a new Markdown string and replace the whole
file. That would destroy unrelated formatting, produce noisy Graft diffs, lose
the user's selection, and make concurrent views conflict unnecessarily.

## Step 3: Activate the UI surface

The UI entrypoint exports one `activate()` function:

```ts
import type { ExtensionFileEditorContext } from "@eidos.space/extension-sdk"

import "./editor.css"
import { parseMarkdownTasks } from "./tasks"

export function activate(context: ExtensionFileEditorContext) {
  function render() {
    const tasks = parseMarkdownTasks(context.document.snapshot.text)
    const list = document.createElement("ul")

    for (const task of tasks) {
      const item = document.createElement("li")
      const button = document.createElement("button")
      button.textContent = `${task.checked ? "✓" : "○"} ${task.label}`
      button.disabled = context.document.snapshot.readOnly
      button.addEventListener("click", () => void toggle(task))
      item.append(button)
      list.append(item)
    }

    context.root.replaceChildren(list)
  }

  async function toggle(task: ReturnType<typeof parseMarkdownTasks>[number]) {
    await context.document.applyEdits([
      {
        start: task.markerOffset,
        end: task.markerOffset + 1,
        text: task.checked ? " " : "x",
      },
    ])
  }

  context.subscriptions.add(context.document.onDidChange(render))
  context.subscriptions.add(context.document.onDidChangeState(render))
  render()

  return { dispose: () => context.root.replaceChildren() }
}
```

The checked-in implementation adds accessible task buttons, progress UI,
empty states, save/error indicators, focus restoration, and responsive styles.
It uses only the mount point in `context.root`.

### Theme the surface

Eidos supplies a small stable token set instead of exposing its Tailwind
classes or internal DOM:

```css
:root {
  font-family: var(--eidos-font-family);
  color: var(--eidos-color-foreground);
  background: var(--eidos-color-background);
}

.task-card:focus-visible {
  outline: 2px solid var(--eidos-color-focus-ring);
}
```

The host updates these variables when appearance changes. Package-local CSS is
compiled from the inspected snapshot; remote styles, fonts, scripts, frames,
and images are blocked by the surface content-security policy.

## Step 4: Validate and compile the example

From an Eidos checkout, run:

```bash
pnpm --filter docs check:examples
```

Expected output includes:

```text
Validated example.markdown-task-board
```

This check now does more than validate JSON. It verifies contribution IDs and
entrypoint paths, then compiles every worker and UI entrypoint through the same
fixed extension compiler used by Desktop. Compiler warnings fail the example
check.

The Task Board parser and interactive surface also have executable tests:

```bash
pnpm exec vitest run \
  apps/docs/tests/markdown-task-board-tasks.test.ts \
  apps/docs/tests/markdown-task-board-editor.test.ts
```

## Step 5: Install it in a local Space

1. Copy the example directory to
   `<space>/.eidos/extensions/example.markdown-task-board/`.
2. Open the Space in Eidos Desktop.
3. Open **Settings → Extensions** and select **Refresh**.
4. Review the package ID, content digest, entrypoint, contribution, and the two
   requested file grants.
5. Select **Trust source** for the exact snapshot.
6. Grant `files.read **/*.tasks.md` and `files.write **/*.tasks.md`.
7. Turn on **Enablement**.

Installation, trust, grants, and enablement are separate decisions. The package
does not run until all applicable decisions allow the same inspected snapshot.

## Step 6: Use and verify it

1. Create `website.tasks.md` and add the sample Markdown from this page.
2. Open the file. The default matching editor should be **Task Board**.
3. Toggle **Finish the landing page**.
4. Confirm the card moves to **Completed**, progress becomes `67%`, and the save
   indicator returns to **Saved**.
5. Use **Open with Eidos** and confirm the raw line is now
   `- [x] Finish the landing page`.
6. Use Eidos undo and confirm every open view returns to the previous state.
7. Edit the file externally while the board has unsaved changes and verify the
   host conflict banner offers **Reload file** or **Keep my changes**.

Only the checkbox marker should appear in the file diff. If the complete file
changes, the extension is bypassing the intended document model.

## Publish from GitHub

Put the package contents at the root of a public repository and tag an
immutable release such as `v0.1.0`. In **Settings → Extensions**, select
**Install from GitHub**, enter the repository and tag, prepare the review, then
install the resolved commit. Eidos does not run `npm install` or repository
lifecycle scripts.

After installation, the user still reviews trust and grants locally. Updating
to another tag creates a new source snapshot and never silently overwrites
locally modified extension files.

## Troubleshooting

| Symptom                   | Check                                                                     |
| ------------------------- | ------------------------------------------------------------------------- |
| Task Board is absent      | The file must end in `.tasks.md`; refresh package discovery.              |
| Package is `Untrusted`    | Review and trust the current content digest, not an older version string. |
| Board is read-only        | Grant both matching read and write capabilities.                          |
| Activation error          | Inspect package diagnostics and compile the example locally.              |
| Edit is rejected as stale | Apply host broadcasts and request `resync()` before retrying.             |
| Save conflict             | Resolve the host conflict banner; never add a direct filesystem fallback. |
