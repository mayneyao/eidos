`@eidos.space/extension-cli` is the non-interactive developer entrypoint for
both people and agents. It creates real source packages and checks them with
the same strict inspector and fixed compiler used by Eidos Desktop.

During the developer preview the CLI is built from an Eidos checkout. It is
prepared for a public npm release, but is not documented as published until
that release exists.

## Create a project

From the Eidos repository root:

```bash
pnpm extension:cli init example.hello-tools --template command

pnpm extension:cli init example.notes-editor \
  --template text-editor \
  --pattern "**/*.notes.md" \
  --display-name "Notes Editor"
```

The extension ID always has the form `<publisher>.<name>`. `init` creates a
directory with that canonical ID and refuses to overwrite an existing
directory. The text-editor starter includes an editable UI surface, minimal
text edits, host save state, resync behavior, and Eidos theme tokens.

Useful options:

| Option                      | Meaning                                                  |
| --------------------------- | -------------------------------------------------------- |
| `--template command`        | Create a Worker command starter.                         |
| `--template text-editor`    | Create an editable sandboxed `fileEditors` starter.      |
| `--out-dir <directory>`     | Choose the parent directory for the new package.         |
| `--engine <semver-range>`   | Set `engines.eidos`; the preview default is `>=0.33.0`.  |
| `--pattern <glob>`          | Set the editor selector and matching read/write grants.  |
| `--media-type <media-type>` | Set the text editor media type; default `text/markdown`. |

## Check a package

Run this from any source repository; its directory does not need to use the
canonical ID until Eidos installs it into a Space:

```bash
pnpm extension:cli check ./example.notes-editor --host-version 0.33.0
```

A successful check reports every compiled entrypoint:

```text
✓ example.notes-editor · ready · v0.1.0
  ✓ ui src/editor.ts (… bytes)
```

The check is deliberately stronger than TypeScript syntax validation. It:

- applies package file, path, size, link, and stable-read limits;
- strictly parses `extension.json` and validates IDs, contributions,
  permissions, entrypoints, and Eidos compatibility;
- rejects unsupported or missing imports;
- performs strict TypeScript checking against the public Eidos SDK;
- compiles declared Worker and UI entrypoints from the exact inspected bytes;
- treats compiler warnings as failures;
- never installs dependencies, reads package-manager configuration, executes
  extension code, or runs lifecycle scripts.

## Agent and CI output

Use JSON when a script or agent needs a stable result:

```bash
pnpm extension:cli check . --host-version 0.33.0 --json
```

Exit codes are intentional:

| Code | Meaning                                                      |
| ---- | ------------------------------------------------------------ |
| `0`  | Package inspection and all entrypoint builds passed.         |
| `1`  | The package is invalid, incompatible, or failed compilation. |
| `2`  | The CLI invocation or filesystem operation failed.           |

The JSON includes status, canonical ID, source and permission digests,
compiled entrypoints, and structured diagnostics. CI should fail on any
non-zero exit instead of parsing terminal text.

## Verify release artifacts

Before publishing the developer packages, Eidos maintainers run:

```bash
pnpm smoke:extension-tooling
```

This is intentionally stronger than running the CLI inside the monorepo. It
builds and packs the manifest, surface protocol, SDK, runtime, and CLI packages,
installs those tarballs into a clean temporary consumer, and then exercises the
installed binary and library API. The gate rejects leaked `workspace:`
dependencies, missing internal packages, version drift, an incorrect CLI
license, a broken executable, and templates that do not respect their Eidos
engine range. Package lifecycle scripts remain disabled during installation.

The reusable **Extension Delivery** workflow runs package metadata validation,
CLI type-checking and tests, the packed-consumer smoke test, and the official
example/documentation build on Node 22. The tooling and packed-consumer checks
run on Linux, macOS, and Windows. Desktop release builds wait for this workflow,
so a developer-kit regression blocks a release instead of shipping an
unusable scaffold or SDK.

This is a delivery gate, not an API-stability promise. During the preview,
extensions must declare `engines.eidos`, pin immutable releases, and expect
documented capability and surface contracts to evolve before a stable v1.

## Publish the developer packages

The five developer packages share one version and release together in
dependency order:

1. `@eidos.space/extension-manifest`
2. `@eidos.space/extension-surface-protocol`
3. `@eidos.space/extension-sdk`
4. `@eidos.space/extension-runtime`
5. `@eidos.space/extension-cli`

Maintainers can inspect a release locally without credentials or registry
writes. The output directory must be empty:

```bash
pnpm release:extension-packages \
  --mode plan \
  --version 0.1.0 \
  --output-dir /tmp/eidos-extension-release
```

The planner requires one exact version across all five packages, rejects
unshipped workspace dependencies and dependency cycles, replaces internal
`workspace:*` ranges with that exact version, and queries npm before choosing
`publish`, `stage`, or `skip`. It writes the tarballs plus their byte counts,
SHA-1, SHA-512 integrity, source commit, and intended action to
`release-plan.json`. It cannot publish from a developer machine.

Actual registry changes use the manual **Extension Package Release** workflow
from the exact tag `extension-tooling-v<version>`. The workflow first runs the
full Extension Delivery gate, builds a review artifact, and pauses at the
protected `npm` environment. The publishing job downloads and revalidates the
reviewed tarballs instead of rebuilding them.

The first release is a one-time bootstrap because npm staged publishing cannot
create a new package. Configure the protected GitHub `npm` environment with
required reviewers and a short-lived `NPM_TOKEN`, select `bootstrap`, and remove
the token after all five packages exist. Then configure an npm trusted
publisher for each package with repository `mayneyao/eidos`, workflow
`extension-package-release.yml`, environment `npm`, and staged publishing only.

Later releases use `stage`: bump all five package versions together, create the
matching immutable tag, dispatch the workflow from that tag, review the staged
packages in npm, and approve them with 2FA. Do not rerun a successful staged
release; inspect the npm staged-packages page first. See npm's official
[trusted publishing](https://docs.npmjs.com/trusted-publishers/) and
[staged publishing](https://docs.npmjs.com/staged-publishing/) documentation for
the registry-side setup.

## Development loop

1. Scaffold outside your primary Space.
2. Edit ordinary source files and run `check` after each meaningful change.
3. Copy the package into
   `<test-space>/.eidos/extensions/<publisher.name>/` and refresh the Extension
   Manager.
4. Review the exact digest, trust it, grant only requested capabilities, and
   enable it.
5. Exercise commands or open a matching file. Verify saves and Graft changes
   with the built-in UI.
6. Run `check` again, commit the package to GitHub, and install an immutable tag
   through **Settings → Extensions**.

Do not add a fallback that directly imports Node.js, Electron, or the host
filesystem when the sandbox rejects an operation. Declare the missing
capability or redesign the extension around the existing host contract.
