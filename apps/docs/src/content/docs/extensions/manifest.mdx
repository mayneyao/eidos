`extension.json` is the authoritative package contract. Eidos parses it without
running extension code, which lets the host show commands, select editors,
review permissions, and reject incompatible packages safely.

Use the machine-readable
[extension manifest schema](/schemas/extension-manifest.schema.json) in editors
and validation tools.

## Identity

| Field             | Required | Meaning                                                                    |
| ----------------- | -------- | -------------------------------------------------------------------------- |
| `manifestVersion` | Yes      | Version of the manifest format. Version `1` is frozen for foundation work. |
| `publisher`       | Yes      | Stable lowercase publisher namespace.                                      |
| `name`            | Yes      | Stable lowercase package name.                                             |
| `displayName`     | Yes      | Human-readable name that may change.                                       |
| `version`         | Yes      | Semantic package version.                                                  |

The canonical ID is `${publisher}.${name}`. Commands and other globally named
contributions must start with this ID.

## Compatibility and entrypoints

`engines.eidos` is a semantic-version range checked before build. `entrypoints`
declares code roots explicitly:

- `worker` — command and non-visual runtime code.
- `ui` — components instantiated in sandboxed UI surfaces.

An entrypoint must stay inside the package directory. Path traversal, absolute
paths, Node built-ins, and non-literal dynamic imports are rejected.

Version 1 resolves only relative package modules and
`@eidos.space/extension-sdk`. Eidos does not run `npm install`, execute package
lifecycle scripts, rewrite imports to a CDN, or resolve arbitrary bare package
imports. Dependencies may be vendored as reviewable source and imported
relatively.

## Contributions

Contributions are declarative. A command can be indexed without activating the
worker; panels, file editors, and Eidos File views can be discovered without loading
their UI bundle.

The file editor contribution `id` is also the stable activation identity passed
to the UI entrypoint; there is no second component ID. In the current Desktop
developer preview, a matching trusted editor opens through the host-owned
TextDocument lifecycle and a sandboxed UI surface.

Menu conditions use a host-parsed expression subset such as:

```text
resourceExtname == .md && resourceIsDirectory == false
```

Version 1 supports `resourceExtname`, `resourceIsDirectory`, and `&&`. Unknown
keys or unsupported syntax fail closed. Conditions are data, never JavaScript
evaluated by the host.

## Permissions

Permissions describe the maximum capabilities the package may request. They do
not grant access by themselves.

```json
{
  "files": {
    "read": ["notes/**/*.md"],
    "write": ["notes/generated/**"]
  },
  "network": ["https://api.example.com"]
}
```

A new permission set changes the permission hash and requires review even if
the extension version string is unchanged.

## Digest and trust

Eidos calculates a deterministic content digest from every installed package
file except the host-managed `extension.lock.json`. Trust is keyed by canonical
ID, content digest, and normalized permission hash. Build cache identity also
includes the host runtime ABI and is never evidence of trust.

## Validation rules

- Unknown manifest keys are rejected in version 1.
- Duplicate command or editor IDs invalidate the package.
- Two packages with the same canonical ID are both blocked until the conflict
  is resolved.
- Third-party packages cannot use the reserved `eidos` publisher.
- Invalid or unsupported manifests never fall back to running an older bundle.
