An Eidos extension is a self-contained package installed inside a Space. The
manifest tells Eidos what the package contributes before any extension code is
executed. Runtime code receives a capability-based SDK instead of raw access to
Electron, Node.js, SQLite, or the host filesystem.

## What extensions can contribute

| Contribution | Purpose | Initial delivery |
| --- | --- | --- |
| `commands` | Named operations available to menus and the command palette | Yes |
| `menus` | Contextual placement of commands | Yes |
| `fileEditors` | Editors or previews selected by file pattern or media type | Yes |
| `folderViews` | Purpose-built views for folders | Later |
| `baseViews` | Grid alternatives such as gallery, kanban, or timeline | Later |
| `agentTools` | Permission-aware tools callable by an agent | Later |
| `configuration` | Host-rendered settings with explicit storage scope | Later |

Legacy `FileAction`, `DocAction`, and `TableAction` records are normalized into
commands plus menu placements. They are not separate package runtimes.

## The developer path

1. Complete the [five-minute quickstart](/extensions/quickstart/).
2. Understand the [package anatomy](/extensions/anatomy/).
3. Define contributions in the [manifest](/extensions/manifest/).
4. Use [lifecycle and activation](/extensions/lifecycle/) correctly.
5. Review the [security model](/extensions/security/).
6. Prepare the package for [GitHub distribution](/extensions/distribution/).

## Core invariant

Installation and execution are separate decisions. A package can be present in
the Space, visible to Graft, and still remain disabled because it is untrusted,
incompatible, missing permissions, or unable to build.
