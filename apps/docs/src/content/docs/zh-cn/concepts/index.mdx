平台建立在少量稳定概念上。UI 功能和扩展 API 应复用这些概念，而不是再创建一套平行的数据模型。

## Space

Space 是用户打开的根目录。扩展能够看到的路径始终相对于这个根目录；`.eidos`、`.graft`
等内部目录不是普通用户路径。

## 文件

文件是默认的互操作边界。Eidos 根据媒体类型和已注册的 file editor contribution 选择编辑器。
没有专用编辑器的文本文件使用简单文本查看器，二进制文件必须有明确的 handler。

## Eidos File

Eidos File 组合了结构化记录、字段、sheet 和 view。Grid、gallery 和 kanban 是同一份记录的不同视图，
不是数据副本。

## 版本历史

Graft 保存变化和 staged snapshot。Eidos 对外提供 Changes、Stage、Commit、Diff 和 Discard，
但不会把 Graft 的存储细节暴露给扩展。SQLite-backed Space 始终保留普通物理 SQLite 文件，
Desktop 使用 Graft CLI 作为版本管理 control plane。
远端同步由 Electron main 通过 Eidos 官方同步服务完成仓库 provision，随后交给 Graft HTTP
Remote v1。OAuth token 只临时传给 CLI，不会写入 remote URL 或仓库配置。
Graft v0.8 的 row diff/merge 也会保留 STRICT、WITHOUT ROWID 数据库的声明主键身份。
物理 worktree 可以使用任意合法 SQLite page size；只有可选 Graft VFS 写入路径仍限制为 4096 字节。

从 Eidos Sync 克隆时默认使用 File Space：仓库文件和根级 `.graft` 会直接放入所选空目录。
Legacy Space 只用于旧数据库 Space，其运行时会恢复到 `.eidos` 下。

## 扩展

扩展是 Space-scoped package。源码可以跟随 Space 进入版本管理；trust decision、build cache、
secret 和 runtime state 保持在本地。扩展不会直接获得 Electron、Node.js、SQLite 或文件系统权限。

## Local-first 是不变量

已安装源码和 Space 数据必须能够离线工作。网络访问是一项显式 capability，不能成为加载扩展的隐式前提。
