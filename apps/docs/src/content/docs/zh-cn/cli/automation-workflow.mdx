可靠的写入顺序是 **context → apply → validate**。它让 Agent 或脚本只读取有界上下文，
避免基于过期数据写入，并证明提交后的文件仍满足指定 validation level。

以下自动化命令都显式传入 `--json`。默认输出面向人类阅读，不属于机器合同。

## 1. 读取有界上下文

```bash
eidos --json context tracker.eidos Tasks \
  --fields Title,Status \
  --limit 50
```

`context` 返回文件 revision、紧凑 schema 与 logical rows。只有需要 stable ID、
system field、settings、relations 和保存视图时才添加 `--full`。

筛选使用可移植 JSON，字段可以用名称或 stable ID：

```bash
eidos --json context tracker.eidos Tasks \
  --where '{"op":"ne","field":"Status","value":"done"}' \
  --fields Title,Status
```

`ne` 是 `eq` 的 Boolean complement，因此 Status 为空也会匹配。需要排除空值时，再添加
`is-not-null` 规则。

## 2. 执行精确修改

把请求保存为 `request.json`，或通过 stdin 传入：

```json
{
  "revision": "1",
  "table": "Tasks",
  "match": { "_id": "019..." },
  "expect": 1,
  "set": { "Status": "doing" },
  "returning": ["Title", "Status"]
}
```

```bash
eidos --json apply tracker.eidos request.json
```

`revision` 拒绝过期工作；`expect` 防止修改范围意外扩大。CLI 在提交前校验 proposed final
state，并返回 `returning` 指定的记录。

## 3. 校验已提交文件

```bash
eidos --json validate tracker.eidos --level full
```

任一步返回非零 exit status，都应视为整个工作流失败。不要根据猜测或不完整解析继续执行。

## 低层操作

已经掌握 stable ID 与 revision state 的自动化仍可以使用 `rows add`、`rows update`、
`rows delete`、`schema-apply` 与 `view-apply`。Schema change 支持在提交前通过真实
transaction path 执行 dry run。

```bash
eidos --json schema-apply tracker.eidos \
  --expected-revision 1 \
  --op @schema-change.json \
  --dry-run
```

从 `schema` 输出中取得稳定的 Table ID 与 `date` / `datetime` Field ID，即可创建
Calendar View：

```bash
eidos --json view-apply tracker.eidos - <<'JSON'
{
  "expectedRevision": "2",
  "changes": [{
    "kind": "create-view",
    "clientKey": "calendar",
    "tableId": "019...",
    "name": "Calendar",
    "type": "calendar",
    "query": {},
    "layout": { "dateField": "019..." },
    "position": "1"
  }]
}
JSON
```

CLI 分配 View ID，并通过 `createdViews` 返回。持久化 View document 中的 query 与
layout 引用必须使用稳定 Field ID，不能使用显示名称。`update-view` 可以显式修改名称、
类型、query、layout 与 position；`delete-view` 删除指定的稳定 View ID。
