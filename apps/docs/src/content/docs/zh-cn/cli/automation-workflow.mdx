最可靠的写入顺序是：**读取上下文（context）→ 应用修改（mutate / apply）→ 校验文件（validate）**。
它能让智能体或脚本获得受限的数据视图，避免基于过期数据写入，并确保提交后的文件仍然满足指定的校验级别。

下面所有自动化命令都显式传入 `--json`。默认输出是面向人工阅读的，不是机器契约。

## 0. 初始化 Eidos Skill

独立 CLI 已经内置智能体工作流所需的 Skill。安装到当前 Space / 项目，或为当前用户全局安装：

```bash
eidos self skill init
eidos self skill init --global
```

不需要 Node.js、`npm` 或 `npx`。使用 `eidos self skill init --space <DIR>` 可指定其他 Space；
如果文件存在本地修改，必须显式传入 `--force` 才会覆盖。

## 1. 读取受限上下文

```bash
eidos --json data query tracker.eidos Tasks \
  --compact \
  --fields Title,Status \
  --limit 50
```

`--compact` 返回文件版本、紧凑 Schema 和逻辑行数据。传入 `--fields` 可限制返回的字段，传入 `--where` 可过滤数据行：

```bash
eidos --json data query tracker.eidos Tasks \
  --compact \
  --where '{"op":"ne","field":"Status","value":"done"}' \
  --fields Title,Status
```

`ne` 是 `eq` 的布尔补集，因此空的 Status 也会匹配。如果需要排除空值，可添加 `is-not-null` 规则。

## 2. 精确应用修改

将请求保存为 `request.json` 或通过标准输入传入：

```json
{
  "revision": "1",
  "table": "Tasks",
  "match": { "_id": "019..." },
  "expect": 1,
  "set": { "Status": "doing" },
  "returning": ["Title", "Status"]
}
```

```bash
eidos --json data mutate tracker.eidos request.json
```

也可以直接使用内联的变更参数：

```bash
eidos --json data mutate tracker.eidos \
  --table Tasks \
  --match '{"_id":"019..."}' \
  --set '{"Status":"doing"}' \
  --expected-revision 1
```

`revision` / `--expected-revision` 会拒绝基于过期数据的操作。CLI 在提交前会校验拟修改的最终状态，并返回修改后的记录行。

## 3. 校验已提交的文件

```bash
eidos --json file validate tracker.eidos --level full
```

任何一步返回非零退出状态码都应视为工作流失败。切勿基于推测或部分解析的输出继续执行。

## 面向智能体的字段与表结构意图命令

对于常见的 Schema 修改，建议直接使用 `schema` 下的意图命令，而不是手写原始操作 JSON。表和字段可以用名称或稳定 ID 引用；CLI 会在带版本检查的事务前自动解析：

```bash
eidos --json schema field add tracker.eidos \
  --table Tasks --name Due --type date \
  --expected-revision 1 --dry-run

eidos --json schema field add tracker.eidos \
  --table Tasks --name Owners --type relation --target-table People \
  --cardinality many --on-delete detach \
  --expected-revision 2

eidos --json schema table update tracker.eidos Tasks \
  --record-label Title --content-field Notes --dry-run

eidos --json schema field update tracker.eidos Estimate \
  --table Tasks --type integer --dry-run

eidos --json schema field update tracker.eidos Owners \
  --table Tasks --cardinality one --dry-run
```

`table update` 覆盖名称、设置、记录标题字段、Markdown 正文字段、位置以及默认表修改。`field update` 覆盖名称、设置、位置、标题字段选择、存储类型转换和原子选项重命名。转换默认采用编辑器推荐的策略；请检查 dry-run 的分类，只有明确要执行 `explicit-lossy` 时才传入 `--confirm-lossy`。File 字段使用附件命令管理，不能直接转换类型。对关联字段执行 `schema field update` 可更改其目标、基数或删除策略。字段的非空约束故意不对外暴露。

当调用方持有稳定的业务键但没有 Row ID 时，使用 `data mutate --key`。它接受单个对象或对象数组，更新单条匹配的行，并在无匹配时新建行。业务键必须是已存储的非空字段，且最多只能匹配一行现有数据：

```bash
eidos --json data mutate tracker.eidos \
  --table Tasks \
  --key "External ID" \
  --insert '[{"External ID":"task-1","Title":"Ship CLI","Status":"doing"}]' \
  --expected-revision 3 \
  --dry-run
```

返回结果中包含 `plan`，指明每个输入的行是 `create` 还是 `update`；dry-run 的 Row ID 是临时的，请使用真正提交时返回的 ID。去掉 `--dry-run` 即可在单次版本更新中提交整批操作。输入的键重复或匹配多条现有数据时，将直接拒绝且不修改文件。

当单个原子批次需要为同一张表混合创建、更新和删除时，使用 `data mutate --changes`：

```bash
eidos --json data mutate tracker.eidos \
  --table Tasks \
  --expected-revision 4 \
  --changes '[
    {"kind":"update","rowId":"019...","values":{"Status":"done"}},
    {"kind":"create","clientKey":"new-task","values":{"External ID":"task-2","Title":"Document"}},
    {"kind":"delete","rowId":"019..."}
  ]'
```

`data mutate` 复用 Runtime 的 RowChange 契约，要么全部成功，要么完全不执行。使用 `--dry-run` 可在不更改版本的前提下检查结果。低级别的 `schema apply` 和 `schema view apply` 命令在智能体已经持有完整稳定 ID 变更文档时依然可用。

## 附件自动化

不要手动复制本地文件并组装 File 字段的 JSON。`data asset import` 命令会在受管的 `assets/` 目录中暂存文件字节，提取规范元数据，执行带版本检查的单元格更新，并在修改失败时清理暂存文件：

```bash
eidos --json data asset import tracker.eidos \
  --table Tasks --row 019... --field Files \
  --source /absolute/path/report.pdf \
  --expected-revision 5
```

重复传入 `--source` 可执行单次原子多文件导入。只有要整体替换单元格时才传入 `--replace`。如果文件已经位于 `.eidos` 文件所在目录的同级或下级目录中，可使用 `data asset attach` 传入 `--uri assets/name.ext` 直接引用，避免复制。

通过 `data asset detach --entry 019...` 移除特定条目，或使用 `--all` 移除全部。分离和替换都会保留物理磁盘文件，因为其他记录可能仍在使用。检查本地路径、字节大小、媒体类型、符号链接及未引用的孤立受管文件：

```bash
eidos --json data asset verify tracker.eidos --diagnostics-limit 100
```

存在断开的引用会导致命令非零退出。孤立素材仅作警告，绝不会被自动删除。遇到 `stale-revision` 时，应重新读取目标行并重新规划，切勿重放旧的附件修改。

## Runtime 公式与查找

使用规范的 Runtime 计算派生字段。在提交前先预览公式源码；结果中会包含推断类型、依赖关系、诊断信息和可选样本值：

公式使用受限的 SQLite 3.45 标量表达式子集。请参考[公式表达式](/zh-cn/user-guide/formula/)了解白名单函数和语法，不要传入任意 SQL 或自创别名。

```bash
eidos --json schema field preview tracker.eidos \
  --table Tasks --name Total \
  --formula '"Estimate" * 2' --type integer
```

带版本检查和 Runtime 预检地创建或更新公式：

```bash
eidos --json schema field add tracker.eidos \
  --table Tasks --name Total --type formula \
  --formula '"Estimate" * 2' --result-type integer \
  --expected-revision 4 --dry-run

eidos --json schema field update tracker.eidos Total \
  --table Tasks --formula '"Estimate" + 1' --result-type integer \
  --expected-revision 4
```

在 Relation 和目标字段就绪后创建 Lookup：

```bash
eidos --json schema field add tracker.eidos \
  --table Tasks --name OwnerScore --type lookup \
  --relation-field Owners --target-field Score \
  --aggregate sum --expected-revision 5
```

`schema table create` 可在初始字段数组中包含公式字段，并使用相同的预检逻辑。Relation 和 Lookup 字段则在依赖的 Schema 存在后添加。

Lookup 聚合方式支持 `values`、`first`、`count`、`sum`、`average`、`min` 和 `max`；需要去重时添加 `--distinct`。当表中包含公式、查找或反向关联时，`data query` 会自动对其求值，因此派生字段也可以被投影、过滤和排序。派生字段在行修改中是只读的。Runtime 会在提交前拒绝无效类型、缺失目标、过期规划和循环依赖。删除公式或查找属于显式破坏性操作：应先预览并在确认影响后传入 `--confirm-lossy`。

## 低级别操作

Schema 修改在提交前支持基于真实事务路径的 dry-run 执行：

```bash
eidos --json schema apply tracker.eidos \
  --expected-revision 1 \
  --op @schema-change.json \
  --dry-run
```

`schema apply` 也接受 Runtime Schema 批次，并在设置、位置、标题字段、类型转换、选项重命名、关联、公式与查找操作中自动解析表名与字段名。CLI 每次调用不共享 Runtime 变更 Token，因此已提交的修改无法跨命令撤销（`undo`）；请使用 Eidos Lite / Graft 历史记录或已知完好的文件副本进行恢复。

基于 `schema dump` 输出中的稳定表 ID 和日期/时间字段 ID 创建日历视图：

```bash
eidos --json schema view apply tracker.eidos - <<'JSON'
{
  "expectedRevision": "2",
  "changes": [{
    "kind": "create-view",
    "clientKey": "calendar",
    "tableId": "019...",
    "name": "Calendar",
    "type": "calendar",
    "query": {},
    "layout": { "dateField": "019..." },
    "position": "1"
  }]
}
JSON
```

CLI 会分配视图 ID 并在 `createdViews` 中返回。视图查询与布局中的引用使用稳定的字段 ID，持久化的视图文档不接受显示名称。`schema view update` 支持显式名称、类型、查询、布局和位置补丁；`schema view delete` 按稳定 ID 删除视图。
