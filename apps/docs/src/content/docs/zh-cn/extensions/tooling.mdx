`@eidos.space/extension-cli` 是面向开发者和 Agent 的非交互式开发入口。它创建真实源码 package，
并使用与 Eidos Desktop 相同的严格 inspector 和固定 compiler 完成检查。

Developer Preview 阶段先从 Eidos checkout 构建这个 CLI。它已经为后续公开 npm 发布做好 package
准备，但在真正发布之前，文档不会声称它已经可以从 npm 安装。

## 创建项目

在 Eidos 仓库根目录运行：

```bash
pnpm extension:cli init example.hello-tools --template command

pnpm extension:cli init example.dashboard --template panel

pnpm extension:cli init example.card-view --template base-view

pnpm extension:cli init example.notes-editor \
  --template text-editor \
  --pattern "**/*.notes.md" \
  --display-name "Notes Editor"
```

扩展 ID 始终使用 `<publisher>.<name>`。`init` 会用这个 canonical ID 创建目录，并拒绝覆盖已经
存在的目录。Panel starter 会打开一个由 command 驱动的 sandboxed tab；Base view starter 使用宿主
分页数据渲染只读记录；text-editor starter 包含可编辑 UI surface、minimal text edit、宿主保存状态、
resync 处理和 Eidos theme token。

常用选项：

| 选项                        | 含义                                                 |
| --------------------------- | ---------------------------------------------------- |
| `--template command`        | 创建 Worker command starter。                        |
| `--template panel`          | 创建由 command 驱动的 sandboxed panel starter。      |
| `--template base-view`      | 创建宿主分页供数的只读 `baseViews` starter。         |
| `--template text-editor`    | 创建 sandboxed `fileEditors` 可编辑 starter。        |
| `--out-dir <directory>`     | 指定新 package 的父目录。                            |
| `--engine <semver-range>`   | 设置 `engines.eidos`；preview 默认值为 `>=0.33.0`。  |
| `--pattern <glob>`          | 同时设置 editor selector 与匹配的 read/write grant。 |
| `--media-type <media-type>` | 设置 text editor media type；默认 `text/markdown`。  |

## 校验 package

可以直接检查任意源码仓库；只有安装到 Space 后，目录名才必须使用 canonical ID：

```bash
pnpm extension:cli check ./example.notes-editor --host-version 0.33.0
```

成功时会列出每个经过编译的 entrypoint：

```text
✓ example.notes-editor · ready · v0.1.0
  ✓ ui src/editor.ts (… bytes)
```

这比 TypeScript 语法检查更严格。它会：

- 应用 package 文件、路径、大小、链接和稳定读取上限；
- 严格解析 `extension.json`，检查 ID、contribution、permission、entrypoint 与 Eidos 兼容性；
- 拒绝不支持或不存在的 import；
- 根据公开 Eidos SDK 执行严格 TypeScript 类型检查；
- 从本次 inspection 得到的精确 bytes 编译 Worker 与 UI entrypoint；
- 把 compiler warning 视为失败；
- 永不安装依赖、读取 package-manager 配置、执行扩展代码或运行 lifecycle script。

## Agent 与 CI 输出

脚本和 Agent 应使用结构化 JSON：

```bash
pnpm extension:cli check . --host-version 0.33.0 --json
```

退出码具有稳定含义：

| 退出码 | 含义                                              |
| ------ | ------------------------------------------------- |
| `0`    | Package inspection 和所有 entrypoint 编译均通过。 |
| `1`    | Package 无效、不兼容或者编译失败。                |
| `2`    | CLI 调用方式或文件系统操作失败。                  |

JSON 包含状态、canonical ID、source/permission digest、编译过的 entrypoint 和结构化 diagnostic。
CI 应根据非零退出码失败，不要解析终端文案。

## 验证发布产物

发布开发者 package 前，Eidos 维护者运行：

```bash
pnpm smoke:extension-tooling
```

这比在 monorepo 内直接运行 CLI 更严格。它会构建并打包 manifest、surface protocol、SDK、runtime 和
CLI，把这些 tarball 安装进一个全新的临时消费项目，然后真实运行已安装的二进制与 library API。
门禁会拒绝泄漏的 `workspace:` 依赖、缺失的内部 package、版本漂移、错误的 CLI 许可证、不可执行的
bin，以及没有遵守 Eidos engine 范围的模板。安装期间始终禁用 package 生命周期脚本。

可复用的 **Extension Delivery** workflow 会在 Node 22 下执行 package metadata 校验、CLI 类型检查与
测试、隔离消费项目 smoke test，以及官方示例和文档构建。Tooling 与 packed-consumer 检查覆盖 Linux、
macOS 和 Windows；Desktop release build 必须等待该 workflow，因此损坏的 scaffold 或 SDK 会阻断发布。

这是一道交付门禁，不代表 API 已经稳定。Preview 阶段的扩展必须声明 `engines.eidos`、固定 immutable
release，并预期已记录的 capability 与 surface contract 在稳定 v1 前仍可能演进。

## 发布开发者 package

五个开发者 package 共用同一个版本，并按依赖顺序一起发布：

1. `@eidos.space/extension-manifest`
2. `@eidos.space/extension-surface-protocol`
3. `@eidos.space/extension-sdk`
4. `@eidos.space/extension-runtime`
5. `@eidos.space/extension-cli`

维护者可以在不使用凭证、也不写入 registry 的情况下本地检查发布计划。输出目录必须为空：

```bash
pnpm release:extension-packages \
  --mode plan \
  --version 0.1.0 \
  --output-dir /tmp/eidos-extension-release
```

Planner 要求五个 package 使用同一个精确版本，拒绝未发布的 workspace dependency 与依赖环，把内部
`workspace:*` 范围替换为该精确版本，并在选择 `publish`、`stage` 或 `skip` 前查询 npm。它会把
tarball、字节数、SHA-1、SHA-512 integrity、源码 commit 与预期动作写入 `release-plan.json`，但不能
从开发者机器真正发布。

真正的 registry 变更必须从精确 tag `extension-tooling-v<version>` 手动运行 **Extension Package
Release** workflow。Workflow 会先运行完整 Extension Delivery 门禁，生成可审阅 artifact，然后在受保护
的 `npm` environment 暂停。发布 job 会下载并重新验证已经审阅的 tarball，不会再次构建另一份产物。

首次发布需要一次 bootstrap，因为 npm staged publishing 不能创建新 package。先为 GitHub `npm`
environment 配置 required reviewer 和短期 `NPM_TOKEN`，选择 `bootstrap`；五个 package 全部存在后立刻
移除 token。然后分别为每个 npm package 配置 trusted publisher：repository 使用 `mayneyao/eidos`，
workflow 使用 `extension-package-release.yml`，environment 使用 `npm`，并只允许 staged publishing。

后续发布使用 `stage`：同步提升五个 package 的版本，创建匹配的 immutable tag，从该 tag 运行 workflow，
在 npm 中审阅 staged package，并使用 2FA 批准。成功 stage 后不要直接重跑；应先检查 npm staged
packages 页面。Registry 端配置参见 npm 官方的
[trusted publishing](https://docs.npmjs.com/trusted-publishers/) 和
[staged publishing](https://docs.npmjs.com/staged-publishing/) 文档。

## 开发循环

1. 在主要 Space 之外创建 starter。
2. 修改普通源码文件，每次有意义的变更后运行 `check`。
3. 把 package 复制到
   `<test-space>/.eidos/extensions/<publisher.name>/`，然后刷新 Extension Manager。
4. 审阅精确 digest，执行 trust，只授予需要的 capability，然后 enable。
5. 运行 command 或打开匹配文件，通过内置 UI 检查保存和 Graft changes。
6. 再运行一次 `check`，把 package 提交到 GitHub，并通过 **Settings → Extensions** 安装 immutable tag。

Sandbox 拒绝操作时，不要增加直接导入 Node.js、Electron 或宿主文件系统的 fallback。应该声明缺少的
capability，或者围绕已有宿主契约重新设计扩展。
