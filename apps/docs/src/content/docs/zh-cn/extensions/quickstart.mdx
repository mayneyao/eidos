本指南开发 **Markdown Task Board**。它把 `*.tasks.md` 文件显示为双栏任务看板，但文件的
source of truth 始终是普通 Markdown。

经过真实编译检查的完整 package 位于
[`apps/docs/examples/markdown-task-board`](https://github.com/mayneyao/eidos/tree/dev/apps/docs/examples/markdown-task-board)。

## 用户使用场景

创建 `projects/website.tasks.md`：

```md
# Website launch

- [x] Choose a domain
- [ ] Finish the landing page
- [ ] Invite beta users
```

启用扩展后，打开这个文件会看到：

- **2 to do**、**1 completed** 和 **33%** 的进度摘要；
- **To do** 与 **Completed** 两个分栏；
- 每个 Markdown task-list item 对应一张 card；
- 由 Eidos 提供的内联保存状态；
- 勾选 card 后移动分栏，但文件格式保持不变。

用户随时可以在文件右键菜单选择 **Open with Eidos**，回到普通 Lexical 编辑器检查或修改原始
Markdown。

## 谁拥有数据

Task Board 只拥有展示，不拥有持久化：

```text
website.tasks.md
       │ 宿主打开一个 versioned TextDocument
       ▼
sandboxed Task Board surface
       │ applyEdits([{ start, end, text: "x" }])
       ▼
Eidos 校验 revision 并记录 undo
       │ autosave + digest compare-and-swap
       ▼
website.tasks.md + Graft 可见的文件变更
```

Surface 不会获得 Electron、Node.js、raw filesystem handle 或 `writeFile()`。Revision、dirty state、
undo/redo、autosave、外部修改冲突，以及同一文件多个 view 的同步，都由 Eidos 宿主管理。

## 第一步：创建 package

在 Eidos checkout 中，先在生产 Space 之外生成可编辑 text-editor starter：

```bash
pnpm extension:cli init example.markdown-task-board \
  --template text-editor \
  --pattern "**/*.tasks.md" \
  --display-name "Markdown Task Board"
```

命令会拒绝覆盖已有文件。CLI 尚未完成首次 npm 发布；当前基于 checkout 的用法和精确校验边界见
[开发工具](/zh-cn/extensions/tooling/)。

生成的 package 从以下结构开始；按照本指南继续加入 `tasks.ts`：

```text
example.markdown-task-board/
├── extension.json
└── src/
    ├── editor.css
    ├── editor.ts
    └── tasks.ts
```

创建 `extension.json`：

```json
{
  "$schema": "https://docs.eidos.space/schemas/extension-manifest.schema.json",
  "manifestVersion": 1,
  "publisher": "example",
  "name": "markdown-task-board",
  "displayName": "Markdown Task Board",
  "description": "Open *.tasks.md files as an editable task board without changing their Markdown format.",
  "version": "0.1.0",
  "engines": { "eidos": ">=0.33.0" },
  "entrypoints": { "ui": "src/editor.ts" },
  "contributes": {
    "fileEditors": [
      {
        "id": "example.markdown-task-board.editor",
        "displayName": "Task Board",
        "selector": [
          {
            "filenamePattern": "**/*.tasks.md",
            "mediaType": "text/markdown"
          }
        ],
        "priority": "default"
      }
    ]
  },
  "permissions": {
    "files": {
      "read": ["**/*.tasks.md"],
      "write": ["**/*.tasks.md"]
    },
    "network": []
  }
}
```

关键设计决定：

| Manifest value        | 效果                                                    |
| --------------------- | ------------------------------------------------------- |
| `entrypoints.ui`      | 构建 DOM surface；这个 package 不需要 worker。          |
| `fileEditors[].id`    | 作为 tab URL 与 activation 共用的稳定 editor identity。 |
| `**/*.tasks.md`       | 普通 `.md` 文件继续使用内置编辑器。                     |
| `priority: "default"` | 匹配文件直接打开看板，不再多弹一个选择器。              |
| read + write grants   | 用户本地批准后，宿主才能打开并保存匹配文件。            |
| 空 `network`          | Surface 中的网络 API 不可用。                           |

修改源码或申请的 permission 会产生新的 inspected snapshot。Trust、enablement 与 grant 只对用户审阅过的
精确 content digest 和 permission hash 生效。

## 第二步：解析 Markdown，但不要重写它

`src/tasks.ts` 扫描 task-list 行，并记录 checkbox marker 的 offset：

```ts
export interface MarkdownTask {
  checked: boolean
  label: string
  line: number
  markerOffset: number
}

const TASK_LINE = /^(\s*[-*+]\s+\[)([ xX])\](?:\s+(.*?))?\s*$/
```

完整 parser 还会忽略 fenced code block，并处理 CRLF 文件。Offset 使用 JavaScript UTF-16 code unit，
与 version 1 surface protocol 一致；即使 task 之前存在 emoji，也不会破坏 edit range。

不要把文档解析成一份新 Markdown，再替换整个文件。这会破坏无关格式、产生嘈杂的 Graft diff、丢失
selection，也会让多个并发 view 更容易冲突。

## 第三步：激活 UI surface

UI entrypoint 导出一个 `activate()`：

```ts
import type { ExtensionFileEditorContext } from "@eidos.space/extension-sdk"

import "./editor.css"
import { parseMarkdownTasks } from "./tasks"

export function activate(context: ExtensionFileEditorContext) {
  function render() {
    const tasks = parseMarkdownTasks(context.document.snapshot.text)
    const list = document.createElement("ul")

    for (const task of tasks) {
      const item = document.createElement("li")
      const button = document.createElement("button")
      button.textContent = `${task.checked ? "✓" : "○"} ${task.label}`
      button.disabled = context.document.snapshot.readOnly
      button.addEventListener("click", () => void toggle(task))
      item.append(button)
      list.append(item)
    }

    context.root.replaceChildren(list)
  }

  async function toggle(task: ReturnType<typeof parseMarkdownTasks>[number]) {
    await context.document.applyEdits([
      {
        start: task.markerOffset,
        end: task.markerOffset + 1,
        text: task.checked ? " " : "x",
      },
    ])
  }

  context.subscriptions.add(context.document.onDidChange(render))
  context.subscriptions.add(context.document.onDidChangeState(render))
  render()

  return { dispose: () => context.root.replaceChildren() }
}
```

仓库内的完整实现还包含 accessible task button、progress、empty state、保存/错误状态、focus 恢复和
responsive style。它只使用 `context.root` 提供的 mount point。

### 使用宿主 theme

Eidos 提供一组小而稳定的 token，不暴露内部 Tailwind class 或 DOM：

```css
:root {
  font-family: var(--eidos-font-family);
  color: var(--eidos-color-foreground);
  background: var(--eidos-color-background);
}

.task-card:focus-visible {
  outline: 2px solid var(--eidos-color-focus-ring);
}
```

Appearance 改变后，宿主会更新这些变量。Package-local CSS 从 inspected snapshot 编译；surface CSP
会阻止 remote style、font、script、frame 与 image。

## 第四步：验证并编译示例

直接使用生产 inspector 与 compiler 检查这个 package：

```bash
pnpm extension:cli check \
  apps/docs/examples/markdown-task-board \
  --host-version 0.33.0
```

结果会包含编译后的 UI entrypoint：

```text
✓ example.markdown-task-board · ready · v0.1.0
  ✓ ui src/editor.ts (… bytes)
```

Eidos 仓库还会把所有官方扩展示例作为一个整体 gate：

```bash
pnpm --filter docs check:examples
```

输出应包含：

```text
Validated example.markdown-task-board
```

这个仓库 gate 不只是 JSON 检查。它会验证 contribution ID 和 entrypoint path，并用 Desktop 相同的固定 compiler
编译每个 worker 与 UI entrypoint；compiler warning 也会让检查失败。

Task Board parser 与交互 surface 还有可执行测试：

```bash
pnpm exec vitest run \
  apps/docs/tests/markdown-task-board-tasks.test.ts \
  apps/docs/tests/markdown-task-board-editor.test.ts
```

## 第五步：安装到 Space

1. 用 Eidos Desktop 打开 Space，进入 **Settings → Extensions**。
2. 点击 **Install from GitHub**，填写：
   - Repository：`mayneyao/eidos`
   - Branch、tag 或 commit：`dev`
   - Package path：`apps/docs/examples/markdown-task-board`
3. 点击 **Prepare review**，核对 resolved commit、source diff 与 permission diff，再点击
   **Install reviewed source**。
4. 审阅 package ID、content digest、entrypoint、contribution 与两项 file grant。
5. 对当前精确 snapshot 点击 **Trust source**。
6. 授权 `files.read **/*.tasks.md` 和 `files.write **/*.tasks.md`。
7. 打开 **Enablement**。

本地开发时，也可以把示例目录复制到
`<space>/.eidos/extensions/example.markdown-task-board/`，再点击 **Refresh**。

安装、trust、grant 与 enablement 是不同决定。只有所有适用决定都允许同一个 inspected snapshot，package
才会运行。

## 第六步：实际使用并验收

1. 创建 `website.tasks.md`，加入本页示例 Markdown。
2. 打开文件；默认匹配 editor 应为 **Task Board**。
3. 勾选 **Finish the landing page**。
4. 确认 card 移到 **Completed**，进度变为 `67%`，保存状态最终回到 **Saved**。
5. 选择 **Open with Eidos**，确认原始行变为
   `- [x] Finish the landing page`。
6. 执行 Eidos undo，确认所有打开 view 都恢复到上一个状态。
7. 在看板存在未保存编辑时从外部修改文件，确认宿主 conflict banner 提供 **Reload file** 与
   **Keep my changes**。

文件 diff 中应该只有 checkbox marker。如果整个文件都发生变化，扩展就绕过了预期 document model。

## 通过 GitHub 发布

把 package 内容放在 public repository 根目录，或者 monorepo 中的独立 package path，推送 `v0.1.0`
这样的 immutable tag。在 **Settings → Extensions** 中选择 **Install from GitHub**，填写 repository、tag
与可选 package path，准备 review，再安装 resolved commit。Eidos 不运行 `npm install` 或 repository
lifecycle script。

安装后，用户仍要在本机审阅 trust 与 grant。更新到另一个 tag 会形成新的 source snapshot，也不会静默
覆盖本地已经修改的 extension file。

## 常见问题

| 现象                     | 检查项                                                               |
| ------------------------ | -------------------------------------------------------------------- |
| 看不到 Task Board        | 文件必须以 `.tasks.md` 结尾，并刷新 package discovery。              |
| Package 显示 `Untrusted` | 审阅并信任当前 content digest，不能只看旧 version string。           |
| Board 只读               | 同时授权匹配的 read 与 write capability。                            |
| Activation error         | 查看 package diagnostics，并在本地编译示例。                         |
| Edit 被判定 stale        | 应用宿主 broadcast，并在重试前调用 `resync()`。                      |
| Save conflict            | 使用宿主 conflict banner 解决，不能增加 direct filesystem fallback。 |
